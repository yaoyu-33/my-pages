旋钮这里的设置它控制什么
Collector --concurrency1同时向 Environment 提交并等待多少题。调成 4 不会让单个模型调用快 4 倍。
Environment max_concurrent_episodes1（lab.yaml）同时实际执行多少 episode。只把 Collector 调成 4，另外的请求仍会排队。
Hermes concurrency / 模型 / provider 容量Hermes 继承 32；外部容量视部署而定下游也有限额。先确认容量，再一起调整 Collector 和 Environment；不要把 FastAPI workers 当成这个旋钮。

尝试并发 2 时，先把 lab.yaml 的 max_concurrent_episodes 改成 2，重启终端 A 的本次服务，再用新结果目录和 --concurrency 2。--num-repeats 2 则是每题采样两次，和同时跑几题是两回事。

中断后重跑，以及“部分结果”的含义

普通 eval run 默认会重写同路径的输出；新实验用新目录。要恢复同一次运行，保留原来的 tasks、routing、materialized inputs 和 rollouts，在完全相同的收集命令后加 --resume。不要重新运行转换脚本生成新 taskset 再冒充原实验。

native task 输入在 task_input 里，当前 Collector 不支持对它应用 --temperature、--max-output-tokens 等顶层 Responses override。请在生成输入或对应 Agent 配置时设置，并用 env resolve 核对。

如果只想查看已完成的一部分，给 eval profile 加 ++allow_partial_rollouts=True；这样没有任何输出的题会被排除。报告时同时列完成数 / 预期数，不能把部分样本的均值当作整套成绩。

读完可以自己回答：
为什么启动成功之后，还需要 eval run？

env start 是把接电话的人安排好；eval run 才是一通通拨电话的 Collector。eval profile 读已有记录做统计，不重新调用模型。它们分别负责服务生命周期、题目执行和结果分析。
