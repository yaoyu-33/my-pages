模型说“调用天气工具”，接下来究竟传什么？

下面是手写的最小字段示意，省略完整请求/响应的其他字段。城市固定为 Paris，方便追踪；天气函数只拼出固定的 cold 文本，没有查询天气网站。

模型输出中的一项

{"type":"function_call",
 "name":"get_weather",
 "call_id":"weather-1",
 "arguments":"{\"city\":\"Paris\"}"}

arguments 是 JSON 字符串。SimpleAgent 用 json.loads() 解码，再把对象当作 HTTP JSON body 发给 Resources。

Agent 放回上下文的一项

{"type":"function_call_output",
 "call_id":"weather-1",
 "output":"{\"city\":\"Paris\",\"weather_description\":\"The weather in Paris is cold.\"}"}

output 装着工具响应文本；同一个 call_id 指出它回答哪次调用。下一轮模型会看到这份观察。

“能调用工具”有三块代码：声明告诉模型有哪些工具，Agent 把调用派发出去，Resources 真正执行函数。改工具名时要让这三处对得上。

动手：不用模型，用几十行 Python 看见 await 的区别

只需要 Python 3.10+ 标准库。先预测：调用 async 函数得到协程对象时，函数体就会执行吗？四个任务都等 0.12 秒，最多放行两个时，会怎样交错？

python3 /path/to/download/async-mini-lab.py

脚本依次运行逐个 await、提前创建 Task 后逐个等、容量 2 的异步等待，以及在 async 函数里调用阻塞的 sleep。脚本在每个场景结束后一次性打印事件数组；看其中的 start/end 顺序和 peak_in_flight，不要只比较耗时。

你在检查什么预期现象
只创建协程对象函数体尚未运行；await 后才进入。
逐个 awaitA 结束才轮到 B；最多一个操作占名额。
先 create_task，再逐个 await四个任务已先被调度，最多四个操作在途；后面的 await 不会撤销调度。
调度并发 + 容量 2最多两个操作在途，等待可以重叠。
并发里混入 time.sleep阻塞 event loop，其他任务无法在这段等待期间继续。

这里的“在途”指已进入受控区域、还没结束的操作，包括正在等待的操作。这个数量不是 CPU 核数或线程数。这个小实验测本地调度，不能预测 Gym / GPU 吞吐。上面的网页时间线仍是另一套教学模拟。

本次用 Python 3.13.14 实测：创建协程后函数体尚未进入；四种模式的峰值在途数依次为 1、4、2、1。计时只描述本机实验，不是 Gym benchmark。源码和这些结果分开保留，下载后可自行重现。

读 README / docs 时的小习惯

把一句文档说明，追到可以核对的代码

  1. 定版本：先确认命令和网页对应的 revision；latest 可能是发布版别名，和 main 并不相同。
  2. 找入口：从命令找到 CLI handler，从 URL 找到路由注册；不要只搜到一个同名函数就停下。
  3. 追分支：看配置默认值、实际调用者和实现。区分“有这个接口”和“这个 provider 真正支持它”。
  4. 做最小核对：先读类型/测试，再做离线或单服务练习；配置解析通过和模型端到端跑通各有自己的证据。
git rev-parse HEAD
rg -n 'def parse|env.yaml|OmegaConf.merge' nemo_gym/global_config.py
rg -n 'environment_server_routes|_native_episode_request_body' nemo_gym/rollout_collection.py
rg -n 'def disconnect|def stop|__aexit__' nemo_gym/sandbox

例如文档描述配置加载顺序时，沿着 GlobalConfigDictParser.parse() 的列表追加与 OmegaConf.merge() 核对；旧 docstring 也可能落后于函数体。先解释真正执行的分支，再决定是否采用文档中的命令。

算一算：2 道题 × 2 次采样，为什么可以留下 5 次执行？

这是一个手写的身份示例：使用本次运行独有的 taskset demo-run，每题两次逻辑采样；A 的第二次采样出现可重试故障，留下记录后又执行了一次。

task_idrollout_idattemptcapture_key
AA-r00A-r0
AA-r10A-r1
AA-r11A-r1-a1
BB-r00B-r0
BB-r10B-r1

答案是 2 道题、4 个计划采样、5 次实际执行。重试没有把 num_repeats=2 变成 3；同一个仍存活的 Hermes session 内，以相同 capture key 和请求正文重发 activation，则可以复用原任务，不额外增加 attempt。

--resume 读取旧输入快照、主结果和失败记录，再决定哪些还需派发。正常写入主结果的 reward=0 也算已返回，不能仅因分数低就自行重跑。硬中断可能没留下完整记录，仍要检查结果覆盖。
