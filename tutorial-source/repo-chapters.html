@@WEATHER_VERIFY@@

上面两段直接取自固定版本源码。注意这个教学 verifier 只检查“有没有调用名为 get_weather 的工具”，不检查城市对不对、天气真不真、最终回答好不好。所以这里的 reward=1 只能说明模型调用了这个工具。

把 SimpleAgent 的长函数缩成 12 行伪代码
# 教学伪代码：省略 cookies、校验、观测、错误处理与步数限制
async def run(task):
    await resources.seed_session(task)
    history = task.messages
    while True:
        reply = await model.responses(history, tools=task.tools)
        history += reply.output
        if not reply.tool_calls:
            break
        for call in reply.tool_calls:
            observation = await resources.tool(call.name, call.arguments)
            history += tool_output(call.id, observation)
    return await resources.verify(task, history)

await 表示“在这里等结果，同时让别的任务先跑”（第 04 章细讲）。同一道题内部的先后顺序不会变：拿到工具结果之后，模型才能看到它。SimpleAgent 对同一轮的多个工具调用也是逐个 await；多道题同时运行，是 Collector 那一层的并发。

小练习：想增加一个 get_humidity 工具，需要改哪里？
答案：工具声明、实现和评分要对齐

在任务的 tools 里声明名称和参数；在 Resources 里注册同名路由并实现处理函数；如果任务目标变了，还要更新 verifier、样例和测试。SimpleAgent 已经能按名字派发任意工具，通常不用改循环。如果只写了工具声明、没有对应的路由，模型仍然可能发起调用，但这个调用无法执行。

核心抽象：先约定“交什么”，再决定“怎么做”

只要协议不变，背后的实现就可以替换；谁拥有哪些状态，决定了组件能否安全地组合。

@@DIAGRAM_CONTRACT@@
PYTHON / 实现侧

Base 定义契约，Simple 补上运行能力

BaseServer 是带配置和 HTTP 客户端的 Pydantic 对象；SimpleServer 在它之上加了 FastAPI / Uvicorn 的启动能力。Agent、Resources、Model 各自的基类再加上自己的路由和协议，具体的 app.py 只写业务逻辑。

这是按职责做的简化，不是严格的单继承树：源码里的 SimpleResourcesServer 等类用了多继承和 mixin。名字里的 “Simple” 也不代表它只做一件小事。

HTTP / 运行侧

跨进程传的是 JSON，不是 Python 对象

调用方把 Pydantic 数据转成 JSON，通过 HTTP 发出去；接收方按类型校验后再执行。self.server_client.post(...) 是一次网络请求，不是直接调用另一个对象的方法。

所以跨组件的调用可能遇到连接失败、响应丢失、重试和超时。后面 session 和 cleanup 的很多设计，都是为了应对这些情况。

接口输入 → 输出容易混淆的地方
模型 /v1/responses消息、工具声明、采样参数 → 模型输出项，以及可用的 usage / token 信息模型可以输出一个 function call，但那只是一段 JSON，工具并没有被执行。
Agent /v1/responses任务上下文 → 一次 activation 的完整输出，中间可能有多轮模型和工具调用路径和模型接口同名，只是为了格式兼容；它做的事比“问一次模型”多得多。
Resources 工具与 /verify工具参数 → 观察结果；任务 + 输出 / 状态 → reward 和诊断信息工具结果告诉 agent 发生了什么；verifier 判断任务是否完成。
原生 Environment /run带 task 和 episode 身份的请求 → 这次 episode 的结果，或结构化的失败Environment 负责流程和清理；怎么判分仍由 Resources 决定。
旧 Agent /runflat row → 带 response / reward 的结果还没迁移的 agent 自己依次调用 seed、responses 和 verify，没有原生 Environment 提供的那些保障。

BaseServer / SimpleServerResources 基类Agent 基类Environment 基类Model 基类

一个任务从输入到结果，会逐步多出哪些信息？

Task：要解什么输入消息、工具 schema、任务元数据 / verifier 数据
↓ 调用 agent
Trajectory：怎么解的message · function_call · function_call_output · 后续消息
↓ 调用 verifier
Outcome：是否有效完成response · reward · mask_sample · failure_kind / reason
↓ 收集与汇总
Artifacts：事后能复核什么输入快照 · rollout 行 · 失败记录 · 汇总报告

原生请求分成 episode_id 和 task 两部分；task_input 里又分为给模型的 responses_create_params 和给 Resources 的 task_data。不同组件的 JSONL 额外字段并不完全相同，读数据时以具体组件为准。

任务身份和执行身份要分开。同一道题可以采样多条 rollout；某条 rollout 遇到基础设施错误时可能重新执行，产生多个 attempt。TaskId 标识题目，EpisodeId(rollout_id, attempt) 标识一次实际执行。分开它们，统计时才能分清自己数的是题数、样本数还是重试次数。后面各章提到身份时，都是指这里的定义。

reward=0 和“没测出结果”是两回事。
mask_sample 表示这个样本是否应该排除在质量统计之外；failure_kind 描述发生了什么，但不会自动决定是否 mask。类型只是提供了表达方式，具体 verifier 必须正确填写。第 11 章的 Pro 案例会指出这个版本里的一个实际缺口。

旧 run / verify 数据契约原生 task / episode 类型成功与失败的持久化

从一条命令到一组正在监听的服务

先看服务是怎么启动的，再看请求是怎么跑的。两条线在服务入口处汇合。

直接跳到本章八步命令路线 ↓ · 每步都有命令、配置、源码片段和预期结果。

读懂 YAML 的三层：实例名 → 组件类别 → 实现目录

# 节选自实际 weather 配置；模型配置由另一个 YAML 提供
example_single_tool_call_simple_agent:     # 1. 此次运行中的实例名
  responses_api_agents:                  # 2. 组件类别 / 根目录
    simple_agent:                        # 3. 实现目录
      entrypoint: app.py                 # 该目录下的入口
      resources_server:
        type: resources_servers
        name: example_single_tool_call   # 指向另一个实例名
      model_server:
        type: responses_api_models
        name: policy_model              # 不是模型权重名称

这样，同一份 simple_agent/app.py 可以启动成多个实例，各自连接不同的资源和模型。每个服务用自己的实例配置启动；调用方通过实例名查到对方的 host / port。policy_model 背后真正的模型 ID 写在它自己的配置里。

config_paths 用来组合多个配置文件；${...} 是引用 / 插值；Gym 还支持 _inherit_from 等扩展。只读一份短配方看不到全部，最终行为要看合并并填充默认值之后的配置。

GlobalConfigDictParser 依次读取额外配置、合并 override、处理继承和名称替换、组合选定的 agent、检查缺失值与配对，最后填充默认值、地址和端口。目的是在创建任何运行资源之前，就暴露配置错误。

RUNHELPER → HEAD SERVER

父进程建立运行环境

RunHelper.start() 先设置运行监控、初始化或连接 Ray，然后在一个线程里启动 Head Server。Head 对外提供完整配置、实例列表，以及存活和就绪查询。

Head 不是请求网关，模型请求不经过它。Gym 启动的子进程直接使用父进程注入的配置；其他客户端可以先从 Head 取配置，再按实例地址直接请求目标服务。

RunHelper._start()HeadServerServerClient.load_from_global_config()

INSTANCE → SUBPROCESS

按配置找到实现，用组件自己的 Python 环境运行

RunHelper 遍历所有带 entrypoint 的服务配置：找到组件目录，准备（或复用）该组件的 venv，再用它的 Python 运行 app.py。父进程把完整配置和当前实例名注入子进程，并保留子进程句柄，用于状态检查和退出时清理。

组件按这个顺序查找：额外搜索根 → 当前工作目录 → 安装包内置目录，所以同名的自定义组件可能覆盖内置实现。第一次启动慢，可能是在安装依赖，不一定是模型慢。

目录搜索与启动命令子进程与配置注入component_search_roots()

APP.PY → FASTAPI → UVICORN

Python 类变成可访问的服务

入口调用具体类的 run_webserver()。公共实现读取实例配置、创建服务对象，调用它的 setup_webserver() 注册业务路由，再加上健康检查以及异常、取消、观测等公共机制，最后交给 Uvicorn 监听端口。第 05 章已经逐段读过这个过程。

所以很多 app.py 末尾只有一行启动代码：重复的网络服务工作放在公共库，路由和业务留在具体类里。

SimpleServer.run_webserver()具体类如何加路由

PROCESS EXISTS ≠ TASK WORKS

等待 Gym 服务和模型 endpoint 可达

父进程先等所有组件启动，再探测配置中的上游模型 endpoint，最后把 Head 标记为 ready。启动中途失败时，会清理已经启动的进程。

注意：这个版本的 endpoint 探测只要对方有 HTTP 响应就算通过，包括 401 / 404。它只说明地址可达，不说明鉴权、工具解析、token 输出或生成是正确的。所以 ready 之后，仍要按用途做一次小规模真实运行（smoke）。

模型 endpoint 探测标准启动失败清理标记 ready 的顺序

COLLECTOR → ENVIRONMENT /RUN

到这里，才开始一题一题地运行

Collector 准备数据行和路由、控制并发，把任务发到对应 Environment 的 /run，再把结果写入文件并汇总。入口要和数据格式匹配；本教程主线用的是原生格式。

gym eval run 默认走完整流程：整理数据 → 启动服务 → 收集 → 关闭服务。加 --no-serve 则只收集，连接已经在运行的服务。这个开关不会修正配置或数据里的错误路由。

两种 eval 入口端到端收集与 finally shutdownCollector 主入口

控制路径：建立这次运行

CLI → 配置 → RunHelper → Head + 组件进程 → 就绪。关心的是：启动哪些服务、用哪份配置、谁负责启动和关闭。

请求路径：处理一道题

Collector → Environment → Agent / Resources → 模型代理 / sandbox。关心的是：这道题的输入、等待、状态和输出。

Ray、async、Uvicorn worker、Slurm：各自解决什么问题？
机制解决什么问题不能据此推断
async / await一个进程在等待 I/O 时，让其他协程继续运行不会因此多出 GPU 或容器容量。
Uvicorn worker用多个服务进程接收请求进程内的 dict / session 不会自动共享；有些 session 服务明确要求只用一个 worker。
Ray部分组件使用的分布式任务执行能力不是所有 HTTP 调用都会变成 Ray task。simple_agent 和天气服务都声明 ray_enabled=False，但 RunHelper 仍会为整次运行初始化 Ray。
Slurm submit为整次运行申请计算资源，启动服务 / driver不是每次工具调用都提交一个 sbatch。

SHARED LIBRARY

nemo_gym/：所有组件共用的类型和机制

base_*.py 定义组件契约；openai_utils.py 定义 Gym 使用的 Responses 数据类型；server_utils.py 提供服务启动和 HTTP 客户端。这里的大文件往往承担多项职责，读的时候先定位到具体的类和方法。

什么时候来这里：所有环境都出现同一种路由、超时、收集或协议问题时。如果只想改某道题的评分，先去对应的 Resources Server。

AGENT HARNESS

responses_api_agents/：谁在驱动模型与工具的循环

simple_agent 用一个 Python 循环读取模型返回的 function call，再请求 Resources 的工具路由。hermes_agent 则把现成的 Hermes harness 放进 sandbox 运行，用 session 和 runner 管理它。

外部 harness 自己负责规划、调用工具和压缩上下文；Gym 的 wrapper 只负责把它接入统一协议，并没有重新实现这些循环。

什么时候来这里：调整多轮策略、工具执行方式、harness 的启动参数或结果转换时。

simple_agent → _create_episode()最适合第一次读的模型 / 工具循环hermes_agent → responses()session、幂等 activation 与容器内 harness
TASK SEMANTICS

resources_servers/：任务的状态和对错

每个子目录实现一类任务的资源、工具和 verifier。常见文件有 app.py、configs/、依赖文件、测试和样例数据；复杂的 benchmark 还会拆出 preparation、verification 等模块。

“资源”可以是天气查询、数据库、浏览器或代码仓库。并不是每个 Resources Server 都需要 Docker，工具也不一定都要经过它的 HTTP 路由。

什么时候来这里：增加任务、修改工具行为、改评分标准，或检查 seed 之后的状态隔离时。

example_single_tool_call/app.py几十行的工具与 verifier 例子swebench_pro/verification.py复杂任务的测试执行和得分判定
MODEL ADAPTER

responses_api_models/：把不同推理后端接到同一个接口

模型代理接收标准请求，转换成上游支持的格式，再把结果转换回来，同时保留可用的 usage / token 信息。openai_model、vllm_model 等是不同的适配实现。

这里的 Model Server 通常不是运行 GPU kernel 的推理引擎：配置一般指向已有的 endpoint。少数本地模型方案也能负责启动推理服务，要看具体实现。

什么时候来这里：上游协议不匹配、流式响应有问题，或采样参数、token 信息没有正确传递时。

COMPOSITION

配方：用现有组件拼出一个任务系统

environments/ 放环境组合，benchmarks/ 放 benchmark 配方和数据准备；nemotron_recipes/ 放特定模型或实验集合的配置。目录名本身不能说明它“已验证”或“可训练”。

nemo_gym/registry.py 负责发现环境 / benchmark；nemo_gym/environment/ 提供 manifest、scaffold、validation 等注册和开发辅助。两者都不是运行 episode 的服务。

什么时候来这里：选用已有 benchmark、换 Agent、换模型或数据，而不改业务代码时。

WHERE WORK RUNS

容器执行和集群提交是两层问题

nemo_gym/sandbox/ 为任务提供 create / connect / exec / stop 等能力；不同 provider 把这些能力映射到 Docker、OpenSandbox 等平台。哪道题拥有哪个 sandbox，仍由调用它的组件决定。

为什么叫 sandbox provider，不叫 sandbox server？

provider 是提供能力的可替换实现；server 是监听请求的服务进程。AsyncSandbox 调用 provider 的 create / connect / exec / stop。Docker provider 可以通过 SDK / daemon 提供这些能力，OpenSandbox provider 则通过 HTTP 连接 OpenSandbox server；provider 本身不需要开一个 Gym HTTP 端口。

所以这两个名字在不同的层：Resources Server → AsyncSandbox → OpenSandbox provider → OpenSandbox server → task container。替换 provider 只改变执行后端；哪道题拥有哪个 sandbox、什么时候评分和回收，仍由 Resources 决定。

provider 协议AsyncSandbox API

nemo_gym/orchestration/ 负责描述和提交一整次运行：模型服务、计算资源、benchmark driver 和作业记录。在这个版本里，submit 只注册了 Slurm executor，入口标记为 experimental；接口可扩展，不等于已经支持所有集群后端。

什么时候来这里：容器创建或连接失败，看 sandbox；GPU 分配、sbatch、整次运行的提交，看 orchestration。

核心设计：每个选择带来什么，又要付出什么

以下是从源码边界总结出的取舍。并不是所有组件都已经迁移到同一种模式。

设计选择换来的能力代价，以及何时用更简单的方案
组件分进程，通过 HTTP 交互Agent、模型、资源可以独立替换和部署，依赖互相隔离；外部 harness 能通过通用接口接入；同一个 benchmark verifier 可以搭配不同的模型和 harness。数据要经过序列化和网络传输，还可能只有部分服务成功。日志也分散在多个服务里，排错时需要沿调用链查找。单机的小实验用进程内函数组合更好调试，但要自己划清可替换的边界。
YAML 组合 + 实例引用同一份实现可以组成多种搭配；模型参数和 benchmark 规则分开维护。合并、继承和默认值会影响最终行为，不能只看单个文件，要检查合并后的配置（resolved config）。写死的脚本更直观，但配置会重复，实验之间更容易漂移。
Responses 风格的轨迹 + 统一模型入口消息、函数调用、工具返回都有结构；模型代理能集中关联请求和轨迹，训练路径可以保留 token 信息。外部 harness 的子 agent、上下文压缩和自带的 usage，不一定能无损放进一个扁平结果；参数、thinking、usage 也可能在适配中丢失。需要逐条路径核对，缺失的信息要明确标出。
Environment 编排，Resources 判分生命周期独立于具体 harness，可以复用，不用每个 harness 再写一遍 seed / verify / cleanup；任务状态和评分资产有明确的所有者。多了一层服务和协议。迁移期间旧 run 和新 episode 并存，要分清走的是哪条路径；旧 agent 可以继续走转发路径，但不具备新生命周期的保障。
Agent 借用 Resources 的环境harness 可以换，任务镜像和评分逻辑仍由 benchmark 控制。所有权、连接 descriptor、重试和 close 返回记录构成了一套额外的协议。
在全新环境里重新评分 patch减少 agent 留下的临时状态、依赖改动和后台进程对评分的影响。额外的启动成本；patch 导出和文件过滤本身也可能出错。
异步 I/O + 多层并发限制大量任务在等模型、工具、容器时，可以共用一个控制进程。限流、取消、重试和下游容量必须一起设计。阻塞调用会卡住整个 event loop，高并发也会加重资源泄漏和排队。
Sandbox provider 抽象同一套任务代码可以接不同的容器平台，业务代码不必绑定某种部署方式。各平台能力不同，connect、PTY、服务端口、TTL 都要按能力检查。统一的 API 不会消除运行时的差异。
进程内状态 + 有上限的 cleanup实现直接，能处理常见失败和请求重试。进程重启后，状态不会自动恢复。跨 worker 共享状态、进程崩溃后的资源回收，都要另外解决。

EVALUATION

测量一个固定策略的表现

输入任务 → 运行 agent → 验证 → 保存轨迹和得分 → 按样本是否有效进行汇总。Gym 在这里负责组织环境交互和测量。看结果时，要同时看成功率、失败 / mask、覆盖率和采样条件。

TRAINING

训练框架用 rollout 和 reward 更新策略

Gym 提供环境交互、轨迹和 reward；NeMo RL、VeRL 等训练框架负责优化算法、梯度计算和参数更新。更新后的权重如何同步到推理服务，是所选训练方案需要协调的集成边界。

需要 token / logprob 的基于当前策略采样的强化学习（on-policy RL），只有最终文本是不够的。Gym 支持携带原生 token 信息的模型响应，也为外部 harness 提供 token capture 和重建路径。如果无法可靠还原训练调用链，应保留诊断信息，并用 mask 标记排除该样本。不能把重新分词（tokenize）的文本当成原始采样轨迹。

train_data_utils.py 处理数据，不是 optimizer；gym eval submit 提交运行，不是训练循环；reward_profile 统计奖励，不会改进模型。后面的 Pro × Hermes 配方，按它的文档是一条评测路径；不能因为 Gym 支持 RL，就认为它可以直接用于训练。
