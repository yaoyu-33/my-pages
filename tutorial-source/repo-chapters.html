先把整个 repo 放到一张地图上

Gym = 公共运行底座 + 可替换组件 + 组合配方 + 数据与结果。

这个仓库同时装着一个 Python 库、一组可运行的服务、许多 benchmark 实现和操作工具。初读时容易把这些东西看成一套庞大的业务代码。先按下面的责任分组，你就能回答：我要理解的行为，是公共机制，还是某个 benchmark 的具体规则？

↓ 选择实现、配置连线

↓ 复用协议和运行机制

↓ 调用外部能力

这是责任关系图，不是完整的 Python import 图。一次部署可以把多个组件放在同一台主机；逻辑上分层不等于必须分配多台机器。

SHARED LIBRARY

nemo_gym/：所有组件共用的语言和机制

base_*.py 定义组件契约；openai_utils.py 定义 Gym 使用的 Responses 数据类型；server_utils.py 提供服务启动与 HTTP 客户端。这里的大文件有多项职责，读时先定位类和方法。

什么时候来这里：所有环境都出现同一种路由、超时、收集或协议问题。只想修改某道题怎么评分，通常先去具体 Resources Server。

AGENT HARNESS

responses_api_agents/：谁在驱动模型与工具循环

simple_agent 的 Python 循环直接读模型的 function calls，再请求 Resources 的工具路由。hermes_agent 则把已有 Hermes harness 放进运行环境，用 session 和 runner 管理它。

外部 harness 自己会规划、调用工具和压缩上下文。Gym wrapper 负责接入契约，并不意味着这些循环都由 Gym 重新实现。

什么时候来这里：调整多轮策略、工具如何执行、harness 的启动参数或结果转换。

TASK SEMANTICS

resources_servers/：题目世界的状态与对错

每个子目录实现某种任务的资源、工具与 verifier。常见文件是 app.py、configs/、依赖文件、测试和样例数据；复杂 benchmark 会再拆出 preparation、verification 等模块。

“资源”可以是天气查询、数据库、浏览器或代码仓库。并不是每个 Resources Server 都需要 Docker，也并不是所有工具都必须经过它的 HTTP 路由。

什么时候来这里：增加任务、修改工具语义、改评分标准、检查 seed 后的状态隔离。

这里的 “Model Server” 通常不是执行 GPU kernel 的推理引擎。配置可指向已有 endpoint；某些本地模型方案另有启动能力，要按具体实现判断。

什么时候来这里：上游协议不匹配、流式响应有问题、sampling 参数或 token 信息没有正确传递。

WHERE WORK RUNS

容器执行和集群提交是两层不同的问题

nemo_gym/sandbox/ 给任务提供 create / connect / exec / stop 等能力；providers 再映射到 Docker、OpenSandbox 等平台。任务的业务所有权仍由调用它的组件决定。

为什么叫 sandbox provider，不叫 sandbox server？

provider 表示提供能力的可替换实现；server 表示监听并处理请求的服务进程。AsyncSandbox 调用 provider 的 create / connect / exec / stop。Docker provider 可以通过 SDK/daemon 提供能力，OpenSandbox provider 通过 HTTP 连接 OpenSandbox server；provider 本身不必开一个 Gym HTTP 端口。

所以这两个名字处于不同层：Resources Server → AsyncSandbox → OpenSandbox provider → OpenSandbox server → task container。替换 provider 改的是执行后端，Resources 仍然决定哪道题拥有哪个 sandbox、什么时候评分和回收。

provider 协议AsyncSandbox API

nemo_gym/orchestration/ 描述和提交整项运行：模型服务、计算资源、benchmark driver 与作业记录。在这个固定版本中，submit 注册的是 Slurm executor，入口标记 experimental；不能把可扩展接口当成已实现所有集群后端。

什么时候来这里：容器创建 / 连通失败看 sandbox；GPU 分配、sbatch、整项任务提交看 orchestration。

sandbox/api.pyprovider-neutral APIorchestration/submit.py选择 executororchestration/jobs.pygym-job.json 与 resolved-config.yaml
OBSERVATION ≠ TRAINING TOKENS

看得到过程，和能用于训练，是不同要求

telemetry/ 负责 traces / metrics 等运行观测；rollout_observability.py 描述 invocation、turn、tool call 等轨迹记录；token_id_capture/ 处理用于训练的精确 token 与调用关系。

最终文本、原生 harness 的 usage、模型调用捕获、训练 token 链是不同证据。一次普通评测不必开启训练 token capture；可训练性还取决于模型和 harness 接口是否保留足够信息。

telemetry/setup.py跨进程观测初始化rollout_observability.py结构化轨迹token_id_capture/consumer.py消费和重建捕获结果外部 harness 训练指南适用前提、精确 token 与 mask

展开对照

02

核心抽象：组件先约定“交什么”，再决定“怎么做”

同一种协议背后可以换实现；边界和所有权决定能否安全组合。

PYTHON / 实现侧

Base 定义契约，Simple 提供常用运行能力

BaseServer 是带配置和客户端的 Pydantic 对象；SimpleServer 增加 FastAPI / Uvicorn 的公共启动能力。Agent、Resources、Model 的基类再补相应路由和协议；具体 app.py 实现业务。

这是职责概括，不是严格单继承树。源码里的 SimpleResourcesServer 等使用多继承和 mixin；“Simple” 也不代表该类只做一件小事。

HTTP / 运行侧

跨进程交的是 JSON，不是 Python 对象引用

调用方把 Pydantic 数据序列化为 JSON，经 HTTP 发送；被调用方按类型校验再执行。self.server_client.post(...) 是网络调用，不是直接调用另一实例的 Python 方法。

因此会出现连接失败、响应丢失、重试、超时；程序内的一次调用成功返回，不再是唯一可能的结果。后面的 session / cleanup 设计就是为这些边界服务。

契约输入 → 输出不要混淆
模型 /v1/responses消息、工具声明、sampling 设置 → 模型输出项和可用的 usage / token 信息模型可以提出 function call；生成这个 JSON 本身还没有执行工具。
Agent /v1/responses任务上下文 → 完整 activation 的输出，内部可包含多轮模型与工具调用同名 endpoint 表达兼容外形，不代表和一次模型推理具有相同执行范围。
Resources 工具与 /verify工具参数 → 观察；任务 + response / 状态 → reward 与验证诊断工具观察告诉 agent 世界发生了什么；verifier 判断任务是否完成。
原生 Environment /run带 task / episode 身份的请求 → 一次 episode 的结果或结构化失败负责流程和清理；具体任务怎样判分仍由 Resources 定义。
旧 Agent /runflat row → 带 response / reward 的验证结果还没有迁移的 agent 自己串起 seed、responses 和 verify。不能套用原生 Environment 的所有限制。

BaseServer / SimpleServerResources 基类Agent 基类Environment 基类Model 基类

一份任务，从输入到结果会增加哪些信息？

Task：要解什么输入消息、工具 schema、任务元数据 / verifier 数据
↓ 调用 agent
Trajectory：怎么解message · function_call · function_call_output · 后续消息
↓ 调用 verifier
Outcome：是否有效完成response · reward · mask_sample · failure_kind / reason
↓ 收集与聚合
Artifacts：后续能复核什么输入快照 · rollout 行 · 失败记录 · 聚合报告

原生输入包含 episode_id 与 task；task_input 再分模型输入 responses_create_params 和给 Resources 的 task_data。task 身份与一次 attempt 身份显式分开。不要假设整个仓库每一行 JSONL 都有完全相同的额外字段。

同一道题可以采样多条 rollout；某条 rollout 遇到基础设施错误又可能有多次 attempt。TaskId 表示任务，EpisodeId(rollout_id, attempt) 表示物理尝试。分开它们，才能判断自己统计的是题数、样本数，还是重试次数。

reward=0 与“没有有效测量”是两件事。
mask_sample 表达这个样本是否应排除在质量统计之外；failure_kind 描述发生了什么，不自动决定 mask。类型只提供表达能力，具体 verifier 还必须正确填写。后面的 Pro 案例会指出这个固定版本中的实际缺口。

旧 run / verify 数据契约原生 task / episode 类型成功与失败持久化

从命令行到一组正在监听的服务

先追“如何启动”，再追“请求怎样运行”。这两条线会在服务入口汇合。

读懂 YAML 的三层：实例名 → 类别 → 实现

# 节选自实际 weather 配置；模型配置由另一个 YAML 提供
example_single_tool_call_simple_agent:     # 1. 此次运行中的实例名
  responses_api_agents:                  # 2. 组件类别 / 根目录
    simple_agent:                        # 3. 实现目录
      entrypoint: app.py                 # 该目录下的入口
      resources_server:
        type: resources_servers
        name: example_single_tool_call   # 指向另一个实例名
      model_server:
        type: responses_api_models
        name: policy_model              # 不是模型权重名称

这让同一份 simple_agent/app.py 可以生成不同实例，分别连接不同资源和模型。服务端用自己的实例配置启动，客户端用引用的实例名查找 host / port。policy_model 的上游具体模型 ID 在它自己的配置里。

config_paths 用来组合文件；${...} 表达引用 / 插值；Gym 还处理 _inherit_from 等扩展。读一份短配方只看到其中一部分，最终行为要看合并与默认值填充后的配置。

RUNHELPER → HEAD SERVER

父进程建立运行上下文

RunHelper.start() 设置观测信息、初始化 / 连接 Ray，然后在一个线程里启动 Head Server。Head 提供完整配置、实例列表、存活与就绪查询。

INSTANCE → SUBPROCESS

按配置找到实现，使用组件的 Python 环境

RunHelper 遍历带 entrypoint 的服务配置，找到组件目录，准备 / 使用该组件的 venv，再用它的 Python 运行 app.py。父进程注入完整配置以及当前实例名，并保留子进程句柄供状态检查和退出清理。

APP.PY → FASTAPI → UVICORN

Python 类变成可访问的服务

入口调用具体类的 run_webserver()。公共实现读取实例配置，创建 server 对象，调用它的 setup_webserver() 注册业务路由，再安装存活检查、异常 / 取消 / 观测等公共机制，最后由 Uvicorn 监听端口。

这就是为什么很多 app.py 末尾只有一行启动代码：重复的网络服务工作在公共库里，而路由和业务还在具体类里。

SimpleServer.run_webserver()具体类如何加路由

PROCESS EXISTS ≠ TASK WORKS

等待 Gym 服务和模型 endpoint 可达

父进程等待组件 spinup，再探测配置中的上游模型 endpoint，最后将 Head 标记为 ready。启动期间失败会触发已启动进程的清理。

这个版本的模型 endpoint 探测接受“对方有 HTTP 响应”，包括 401 / 404；它证明可达，不证明鉴权、工具解析、token 输出或真实生成正确。因此 readiness 后仍需要与用途相符的 smoke。

模型 endpoint 探测标准启动失败清理标记 ready 的顺序

COLLECTOR → ENVIRONMENT /RUN

现在才进入一题一题的运行

Collector 准备行和路由、控制并发，将任务发到绑定的 Environment /run，把结果写到文件并做聚合。本教程的 Environment 主线按原生生命周期运行；具体入口要与数据协议匹配。

gym eval run 默认走端到端路径：整理数据、启动服务、收集、最后关闭服务；--no-serve 走只收集路径，连接已经运行的服务。配置 / 数据必须匹配，开关本身不会修正错误路由。

两种 eval 入口端到端收集与 finally shutdownCollector 主入口

控制路径：建立这次运行

CLI → config → RunHelper → Head + 组件进程 → readiness。关心哪些服务、哪份配置、谁来启动和关闭。

请求路径：处理这一道题

Collector → Environment → Agent / Resources → Model proxy / sandbox。关心这次任务的输入、等待、状态和输出。

Ray、async、Uvicorn worker、Slurm：各在解决什么？
机制主要问题不要据此推断
async / await一个进程里等待 I/O 时让其他协程继续没有自动得到更多 GPU 或容器容量。
Uvicorn worker多个服务进程接请求进程内 dict / session 不自动共享；某些 session 服务明确限制单 worker。
Ray被相关组件使用的任务 / 集群执行能力不是所有 HTTP 调用都转换成 Ray task。simple_agent 和天气服务都声明 ray_enabled=False；RunHelper 仍初始化运行级 Ray。
Slurm submit为整项运行申请计算资源并启动服务 / driver不是每一次工具调用都提交一个 sbatch。

# 教学伪代码：省略 cookies、校验、观测、错误处理与步数限制
async def run(task):
    await resources.seed_session(task)
    history = task.messages
    while True:
        reply = await model.responses(history, tools=task.tools)
        history += reply.output
        if not reply.tool_calls:
            break
        for call in reply.tool_calls:
            observation = await resources.tool(call.name, call.arguments)
            history += tool_output(call.id, observation)
    return await resources.verify(task, history)

这里 await 表示可以把等待时间让出来；同一题仍有因果顺序：拿到工具结果以后，模型才知道它。这个 SimpleAgent 对同一轮多个工具调用按 for 循环逐个 await；Collector 同时运行多道题是另一层并发。

核心 design：它优先解决哪些变化？

下面是根据源码边界总结的设计取舍，不表示所有组件都已经完全迁移到同一种模式。

选择带来的能力代价 / 何时选择更简单的方案
组件分进程、通过 HTTP 交互Agent、模型、资源可以独立替换和部署；依赖可隔离；外部 harness 能通过通用接口接入。多出序列化、网络和部分失败。单机固定小实验可用进程内函数组合，调试更直接，但需要自己组织可替换边界。
YAML 组合 + 实例引用同一实现可复用为多种 pairing；模型参数与 benchmark 规则分别维护。合并、继承、默认值可能隐藏行为。读 resolved config；固定不可变脚本虽直观，但重复配置和实验漂移更难管理。
Responses 风格的轨迹消息、函数调用、工具返回有结构；可连接模型代理、评测结果和训练数据。外部 harness 的子 agent、压缩、native usage 可能无法无损映射到一个扁平结果，需要附加记录、身份和明确的缺失信息。
Environment 编排，Resources 判分生命周期可以独立于具体 harness 复用；任务状态与评分资产有明确的所有者。多一个服务 / 协议层；迁移期间同时存在旧 run 与新 episode。简单旧 agent 可继续走 relay，但不能假装已经具有新生命周期保障。
异步 I/O + 多层并发限制大量任务等待模型、工具、容器时可以共享控制进程。限流、取消、重试和下游容量必须一起设计。阻塞调用会卡住同一 event loop；高并发也会放大泄漏与排队。
Sandbox provider 抽象任务执行可连接不同容器平台，业务代码少绑定某一种部署。平台能力并不相同，connect、PTY、服务端口和 TTL 都需按能力检查。provider API 统一不能自动消除运行差异。

训练框架用 rollout 和 reward 更新策略

Gym 提供环境交互、轨迹与 reward；NeMo RL、VeRL 等训练框架组织优化算法、梯度计算和参数更新。权重更新与推理服务同步是集成边界，需要由选用方案协调。

对于需要 token / logprob 的在线策略优化，最终可读文本还不够。Gym 既支持携带原生 token 信息的响应，也提供外部 harness 的 token capture / 重建路径。训练调用链不能可靠还原时应保留诊断并 mask，而不是把重新 tokenize 的文本冒充原始采样轨迹。

train_data_utils.py 负责数据，不等于实现了 optimizer；gym eval submit 负责提交运行，不等于训练循环；reward_profile 负责测量奖励行为，不会自动改善模型。本教程后面的新 Pro × Hermes 配方按其文档是评测路径，不能仅因 Gym 支持 RL 就宣称它已经可训练。
