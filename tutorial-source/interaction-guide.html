  1. 先选执行分支。 没有绑定 agent session 的请求，可以使用适配器支持的宿主机路线。Episode session 使用 sandbox。无效或已关闭的 session 不能因此回退到宿主机执行。连接 sandbox 失败时，不能悄悄改到宿主机运行。
  2. 跟着 Python 调用走。 app.py 分发请求，sandbox.py 提供 harness 专用的回调函数（hooks），SandboxSession 协调执行、收集产物和释放资源。
  3. 跨进 sandbox。 Provider 执行命令、传输文件。上传进去的 process_supervisor.py 启动 sandbox_runner.py，再由它调用 harness。其余共享辅助代码仍在 Agent Server 上运行。
  4. 找到模型请求的箭头。 发 HTTP 模型请求的是 harness。这条 Hermes 路线使用 Chat Completions，Agent Server 对外却提供 Responses 接口。Supervisor 负责管理进程，不转发模型请求。
哪两边通信？传的是什么？为什么要分清？
Gym 服务 ↔ Gym 服务HTTP + JSON；FastAPI 处理路由HTTP 方法和路径决定进入哪个处理函数。
Agent Server ↔ sandboxProvider 的命令执行与文件传输Provider 是可替换的实现，可以用 HTTP(S)、gRPC、CLI 或本地子进程。
Supervisor → harness 小程序命令行参数（argv）和操作系统信号这层管理进程的启动与结束。
Harness → Model ServerHTTP 模型请求保留带 rollout 标识的 base URL，确保 sandbox 能访问它。
Sandbox → 适配层下载文件：cleanup.json 和 harness 输出清理证据与任务输出回答的是不同的问题。

较新版本的代码地图 · 2026-10-06 核对。 图源为 PR #3917 的 d40a554c，核对时仍未合并；共享生命周期代码来自已合并的 #3961，版本为 cbb3e065。本页原有的示例和历史 benchmark 保留各自的版本。这两张图是源码讲解，不是新运行的结果。

SWE-Pro 还要多看一步。 它在 /verify 内导出 patch 并停止任务 sandbox A，然后在全新的 sandbox B 里评分。图中简化了 verifier 内部的这些步骤。最后的清理只会停止仍然存在的 sandbox。查看评分器代码。

和小豆一起读图

  1. 准备。 Environment 调用 Resources 的 /seed_session，把返回的 SandboxAccess 交给 Agent session。运行环境（runtime，包括 harness 及其依赖）在 seed 阶段准备。
  2. 执行。 一次 Agent /v1/responses 请求可以包含很多轮模型和工具调用。Harness 从 sandbox 内发出模型请求。
  3. 先确认清理，再收集输出。 适配器检查清理记录，确认 harness 及其子进程已停止，然后收集输出。仅有一个正常的 output.json，不能证明子进程都已停止。
  4. 先关闭 Agent，再评分。 Agent close 必须成功，Environment 才会调用 Resources 的 /verify。Agent 关闭自己的会话，断开与 sandbox 的连接，任务 sandbox 仍保留给评分器使用。
  5. 最后由所有者收尾。 Resources 关闭自己的会话，清理仍然保留的 sandbox 状态。如果另一种模式下由 Agent 显式创建 sandbox，则由 Agent 负责销毁。

Async 在哪里起作用？ 处理请求的协程可以用 await 等待网络或 provider 的 I/O。这时，其他 episode 可以继续运行。但同一道题仍要遵守依赖顺序：先创建再连接，先清理再收集，先关闭 Agent 再评分。可以回看第 04 章的 async 实验。

中途被打断怎么办？ Close 会等待正在进行的收尾；如果清理失败，可以再次调用 close 重试。输出只尝试收集一次。对于借来的 sandbox，无法确认清理时必须报错，不能直接继续评分。确认清理后，先收集可用的输出，再删除会话文件。所有权和重试详见第 12 章。
