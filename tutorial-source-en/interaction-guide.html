PR #3917 · CODE BOUNDARIES

Who runs where, and what crosses each boundary?

The Agent Server is an adapter outside the task sandbox. The harness runs the model-and-tool loop. Start at app.py, follow one execution branch, then look for the arrow to the Model Server.

Read it with Bean

  1. Choose the execution branch. A request with no agent session can run the harness on the Agent Server’s host, if the adapter supports it. An episode session uses a sandbox. An invalid or closed session must never fall back to host execution. A failed sandbox connection must not silently switch to the host.
  2. Follow the Python calls. app.py dispatches the request. sandbox.py supplies harness-specific hooks. SandboxSession coordinates execution, collection and release.
  3. Cross into the sandbox. The provider executes commands and transfers files. The uploaded process_supervisor.py starts the shim: a small script that invokes the harness. The other shared helpers stay on the Agent Server.
  4. Find the model arrow. The harness sends HTTP model requests. For this Hermes path it uses Chat Completions, even though the Agent Server exposes Responses. The supervisor manages processes; it does not proxy model requests.

Read one episode from top to bottom

Each vertical line is a participant. Read the arrows from top to bottom. This is the successful path for a Resources-owned sandbox. It shows order and ownership, not measured latency.

SWE-Pro has one extra detail. Its verifier exports the patch and stops task sandbox A during /verify, then grades in a fresh sandbox B. The diagram simplifies those verifier internals. The final cleanup step stops a sandbox only if it is still present. Read the verifier.

Read it with Bean

  1. Prepare. Environment calls Resources /seed_session and passes its SandboxAccess to the Agent session. The runtime—the harness and its dependencies—is prepared during session setup (seed).
  2. Run. One Agent /v1/responses request can contain many model and tool calls. The harness sends model requests from inside the sandbox.
  3. Confirm cleanup, then collect. The adapter checks the process-tree cleanup receipt and collects harness output. A valid output.json alone does not prove that child processes stopped.
  4. Close the Agent, then grade. Agent close must succeed before Environment calls Resources /verify. The Agent closes its session and disconnects from the borrowed sandbox; the task sandbox remains available for verification.
  5. Let the owner finish. Resources closes its session and releases any remaining sandbox state. If the Agent explicitly created its own sandbox in another mode, the Agent owns that teardown.

Where does async fit? The coroutine handling a request can await network or provider I/O. Other episodes can run while it waits. This episode still has to wait for each dependency: create before connect, cleanup before collection, Agent close before grading. See the async lesson.

If the run is interrupted: the close request waits for finalization to finish. If cleanup fails, close can be called again to retry it. Output collection is attempted once. For a borrowed sandbox, return an error and skip grading if cleanup cannot be confirmed. Available output is collected after cleanup and before session files are removed. See the lifecycle chapter for ownership and retries.
