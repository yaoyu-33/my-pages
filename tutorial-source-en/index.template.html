Gym’s basic idea: It breaks an agent's work in a task environment into components you can combine. The shared library defines protocols and runtime behavior. Individual components handle the model, harness, task state, and scoring. YAML selects the combination for each run.

Terms you will see throughout

Keep these names in mind as you read. They match the names you can search for in the code.

Task · TaskIdOne problem to solve. taskset + task_id identifies the task set and the task within it.
rollout · attemptA rollout is one sample for a task. Each execution of that sample is an attempt, including reruns after infrastructure failures. The rollout ID and attempt number form an EpisodeId.
episodeOne attempt's full lifecycle: setup, execution, scoring, and cleanup.
CollectorThe client program that reads tasks in batches, sends requests, and saves results.
harness · AgentThe program that runs the model ↔ tool loop, such as SimpleAgent or Hermes. An Agent Server exposes it as a Gym service.
Model Server (model proxy)A Gym service that forwards model requests, adapts protocols, and records calls. Actual inference runs in a backend such as vLLM or NIM.
Resources · verifierResources manages task state and tools. Its verifier scores the task and returns a reward.
EnvironmentThe service that coordinates an episode. It calls Resources and Agent in order and handles cleanup.
seed · sessionSeed prepares state before a task starts. A session holds that task's state on the server. A cookie or session ID retrieves it.
activationEnvironment asks Agent to complete a task through one /v1/responses call. That call can contain many model and tool turns.
sandboxA shared interface for an execution environment. The provider determines its isolation. This tutorial uses a container backend: task container A serves the agent, and clean grading container B runs verification.
Typed request · flat row · smoke runA typed request separates task identity from episode identity. A flat row is the older format with fields at the top level of a JSONL row. A smoke run uses one or two real tasks to check that the components work together.

03

Serving: keep a program ready to accept requests

Identify the services, their clients, and the machines where they run.

@@DIAGRAM_SERVING@@

A regular script often follows “start → finish a job → exit.” A service process keeps listening on a port. When a request arrives, it runs the matching function and returns the result. For example, POST /verify is an HTTP request. The host and port select the service. The path selects an endpoint, and the JSON body carries the data for this call.

GYM SERVING

Turn a Python component into an HTTP service

FastAPI maps URLs to Python functions. Uvicorn listens on a port and handles network connections. An Agent Server may only run control logic. A Resources Server may spend most of its time waiting for containers and tests.

gym env start starts the configured Gym services. Successful startup does not mean a task has finished.

MODEL SERVING

Load weights onto GPUs and generate tokens

Inference backends such as vLLM and NIM load model weights, manage GPU memory and request queues, and run inference. Gym's Model Server sits in front of the backend. It adapts protocols, handles request parameters, and links calls to trajectories.

If you already have a model endpoint, Gym connects to it. Starting Gym's model proxy does not allocate GPUs, submit Slurm jobs, or load a checkpoint.

B · Task sandbox: local Docker or a remote provider; a GPU is not always needed

Inside a task container, localhost refers to that container. It does not automatically reach the Gym proxy on your workstation. 04

Async: while one task waits, another can continue

Waiting for the network, model, or container often takes much longer than the Python computation itself.

@@DIAGRAM_AWAIT@@

Think of the event loop as a scheduler. When a coroutine reaches an await for unfinished async I/O, it yields control. It resumes there when the result arrives. The order within that coroutine stays the same: create the sandbox before connecting to it; receive a model's tool call before running that tool.

INTERACTIVE LESSON · 4 REQUESTS

Change how requests wait and compare the timelines

Teaching simulation, not a measurement

Each request does 0.25 s of local work, waits 3 s for external I/O, then does another 0.25 s of local work. External I/O can overlap without interference. Local work on the same event loop still runs one request at a time. The simulation does not model GPU batching, network congestion, or retries.

Fixed scale: 0–14 seconds
Compare all three modes on the same scale

Concurrency does not mean all computation runs in parallel

A Python event loop executes one task's Python code at a time. Waiting can overlap. Model batching and computation across multiple GPUs belong to a different layer of scheduling.

Calling synchronous network functions inside async def, or calling time.sleep(), still blocks that event loop. Using asyncio.to_thread() for a synchronous function can avoid this, but canceling the wait does not automatically stop that thread or a remote process.

Semaphore: limit concurrent work

Allowing two tasks to run at once does not mean there are two GPUs. It also does not guarantee that at most two containers exist. A concurrency limit applies only at the layer where it is placed.

In this recipe, Hermes (the agent in chapter 09) uses sem to limit activations only. Resources seed and agent seed happen before it, so this limit does not cover them. To control resource use across whole episodes, check Collector limits and the Environment’s limits on active episodes.

12

Lifecycle: completion, retries, and scoring are separate

Session and cleanup code has to account for uncertain behavior in remote systems. That is why there is so much of it.

@@DIAGRAM_LEASE@@

How identity works during retries

Recall chapter 02: TaskId identifies the problem, rollout_id identifies one logical sample, and attempt distinguishes executions after recovery. The corresponding capture_key looks like r42, r42-a1, and so on.

Within the same live Hermes session, retrying an activation with the same capture key and request body joins the existing state.task. A changed body gets 409. This guarantee does not cover replaying the whole Environment /run call or restarting the service process. Before creating a new attempt, inspect the original execution's state and the Collector records.

Cookies and descriptors have different jobs

The session cookie lets Resources retrieve the task's server-side state. SandboxAccess carries the provider reference, serialized connection descriptor, and workdir=/app so Agent can connect to the same sandbox.

A descriptor contains connection details. It does not copy the container or transfer lifecycle ownership. A borrower uses disconnect(); the owner uses stop().

Why close the agent before verification?

Suppose a shell tool starts a background process. The model says “I'm done,” but the process keeps writing files. Exporting a patch now would race with those writes and could affect scoring. The new path first gets Agent's close receipt and confirms runner cleanup. Resources then exports the patch, stops the task sandbox, and uses a fresh sandbox for grading. An HTTP response does not prove that the remote process tree has stopped.

There is no single timeout for everything

REQUEST / COMMAND

How long can one call wait?

The model HTTP timeout limits one model request. The terminal timeout limits one shell command. Increasing either will not fix a wrong address.

Runner / Episode

How long can the whole process run?

The runner budget limits the Hermes loop. The episode also includes seed, agent close, and verify. If the outer budget is too short, it cancels the task before the inner work finishes.

Cleanup / TTL

How long can resources remain after a stop?

Cleanup has its own time limit, separate from the episode deadline. The sandbox lease must cover its actual lifetime. A timeout response does not mean the container has disappeared.

Some inherited defaults in this recipe are: Hermes 30 turns, terminal 60 s, runner 21600 s; Environment episode 21600 s, cleanup 180 s; Pro test command 3600 s, one verification attempt 1200 s, total verification 2700 s. One verification attempt expires at 1200 s, before the test command's 3600 s limit. These limits cover different scopes. Adding them does not give the total runtime. They have not been validated for your target tasks.

Why not simply add more FastAPI workers?

A worker is a service process, not a coroutine. In this version, the Pro session map is an in-process dictionary, so num_workers != 1 raises an error. Hermes sessions also require one worker. A request sent to another process cannot find the session in the original process.

Environment supports multiple workers, but each has its own semaphore and queue for waiting episodes. Total capacity is roughly workers × max_concurrent_episodes. More workers do not remove the limits of stateful downstream services. First tune Collector and episode concurrency and observe downstream capacity. Then consider state sharing or routing across processes.

Code detail: can async with clean up a borrowed sandbox?

First check what the context manager does on exit. In this version, AsyncSandbox.__aexit__() always calls stop(), including on objects returned by connect(). A borrower must not destroy the task container this way. Hermes first confirms that its runner has stopped and keeps the cleanup evidence, then calls disconnect(). Resources still needs to export the patch before it stops the sandbox.

Compare with Harbor: how should you organize the work?

Start with the capabilities you need, then choose a framework. Chapter 08 covers Gym's internal design choices. This chapter compares Gym and Harbor.

@@DIAGRAM_COMPARE@@

How Harbor organizes the same work

Here, Harbor means an agent evaluation framework. It organizes work as Task → Trial → Job. A task usually has instructions, an environment definition, and tests. A trial is one agent attempt at a task. A job manages many trials. The official agent list currently includes Hermes, and Harbor provides the ATIF trajectory format. Official agent capability table

Three options, depending on your tasks

Run existing Harbor tasks sooner

Use Harbor directly

A good fit when tasks already use Harbor format and the goal is agent evaluation. If you later need Gym's data or training interfaces, you will need a bridge and must check that the meanings of its fields match.

Existing Gym data and verifiers

Use native Gym components

A good fit for reusing Resources, model access, and infrastructure shared across environments. The cost is more service and session management. This native Hermes recipe is also currently limited to evaluation.

Existing assets in both frameworks

Gym + Harbor bridge

A good fit for keeping Harbor trials while using Gym's result and model interfaces. You must maintain versions, timeouts, artifacts, and failure mappings across both layers.

These choices are engineering judgments based on interfaces and code, not speed or accuracy experiments. A single-process script is also a reasonable starting point. Deployment is simpler, but you must manage concurrency, resume, cleanup, and scoring records yourself. If you need durable recovery across hosts, consider a workflow engine. That adds operational work and idempotency design. This tutorial does not establish a need to migrate.

Check your understanding of the repository

① Does a ResourcesServer always need a container?

No. It manages task resources and verification. The weather example just returns a Python object. The task determines whether a sandbox is needed.

② How do an instance name, implementation directory, and upstream model name differ?

The instance name identifies a node in this configuration. The implementation directory selects the code to load. The upstream model name identifies the model sent to the inference service. For example, policy_model can be the instance name of a vllm_model proxy.

③ Why is reading only nemo_gym/ not enough to understand a benchmark?

The shared library provides reusable mechanisms. Components and recipes supply task data, tools, and scoring rules. Reading only one app.py also misses shared startup, routing, and collection behavior.

④ Does every /run use the same base-class lifecycle?

No. A native Environment wraps run with BaseEnvironmentServer's run_request. legacy_agent registers its own forwarding route to the older Agent.run. Check each setup_webserver to see which path it uses.

Check your understanding of the benchmark

① The model says “fixed,” but the patch is unchanged. Which should you trust?

Trust the actual state and verifier. SWE-Pro exports the candidate patch from the task sandbox's git diff and grades it in a clean environment. A claim in the final answer does not prove that a test passed.

② Why can raising async concurrency from 2 to 32 make a run slower?

The model queue, container capacity, connection pool, or test resources may saturate first. That increases waits and timeouts. Coroutines can wait on more requests, but they do not add downstream capacity. Measure stage latency and resource use before changing limits.

③ Why is it a bug if Agent stops a borrowed sandbox?

Resources still needs to extract the repository changes. Agent should clean up its own processes, then disconnect. Resources owns the task sandbox and stops it after exporting the patch.

④ Do the native entry example in chapter 13 and the recorded run in chapter 11 validate the same things?

No. Both use Environment → hermes_agent native sessions. The recorded run still used an outer flat-row adapter; chapter 13 accepts typed requests directly. Their source versions and budgets also differ. A real run has validated the internal lifecycle, but this new entry-point setup has not run end to end with a model.
