Verifier: define what counts as success

@@WEATHER_VERIFY@@

Both snippets above come directly from the pinned source. This teaching verifier only checks for a tool call named get_weather. It does not check the city, the weather, or the quality of the final answer. Here, reward=1 only means the model called that tool.

SimpleAgent’s long function, reduced to 12 lines of pseudocode
# Teaching pseudocode: cookies, validation, tracing, errors, and step limits omitted
async def run(task):
    await resources.seed_session(task)
    history = task.messages
    while True:
        reply = await model.responses(history, tools=task.tools)
        history += reply.output
        if not reply.tool_calls:
            break
        for call in reply.tool_calls:
            observation = await resources.tool(call.name, call.arguments)
            history += tool_output(call.id, observation)
    return await resources.verify(task, history)

await means “wait here for the result, while allowing other tasks to run” (more in Chapter 04). Steps within one task still have an order: the model can only see a tool result after it arrives. SimpleAgent also awaits tool calls from the same model turn one at a time. The Collector provides concurrency across separate tasks.

Try it: Where would you make changes to add a get_humidity tool?
Answer: align the declaration, implementation, and scoring

Declare the name and arguments in the task’s tools. Register a route with the same name in Resources and implement its handler. If the task’s goal changes, update the verifier, examples, and tests too. SimpleAgent already dispatches tools by name, so its loop usually needs no changes. With only a declaration and no matching route, the model can request the tool, but the call cannot run.

Core abstractions: agree on the contract, then choose the implementation

A stable protocol lets you swap implementations. Clear state ownership lets components work together safely.

@@DIAGRAM_CONTRACT@@
PYTHON / IMPLEMENTATION

Base defines the contract; Simple adds server support

BaseServer is a Pydantic object with configuration and an HTTP client. SimpleServer adds FastAPI / Uvicorn startup support. The Agent, Resources, and Model base classes add their routes and protocols. Each concrete app.py then implements the task-specific behavior.

This is a simplified view of responsibilities, not a strict single-inheritance tree. Classes such as SimpleResourcesServer use multiple inheritance and mixins. “Simple” in a class name does not mean the class does only one small thing.

HTTP / RUNTIME

Processes exchange JSON, not Python objects

The caller serializes Pydantic data as JSON and sends it over HTTP. The receiver validates the data before handling it. self.server_client.post(...) sends a network request; it does not call a method on another Python object.

Calls between components can fail to connect, lose a response, retry, or time out. Many of the session and cleanup rules below address these cases.

A native request has two parts: episode_id and task. Inside task_input, the model receives responses_create_params and Resources receives task_data. Extra JSONL fields differ between components, so check the component you are using.

Keep task identity separate from execution identity. One task can produce several sampled rollouts. An infrastructure failure may cause a rollout to run again, creating several attempts. TaskId identifies the task; EpisodeId(rollout_id, attempt) identifies one execution. Keeping them separate helps you count tasks, samples, and retries correctly. Later chapters use these same definitions.

reward=0 differs from “no valid result.”
mask_sample says whether to exclude the sample from quality metrics. failure_kind describes what happened, but does not decide masking by itself. The types provide fields; each verifier must fill them correctly. The Pro case in Chapter 11 shows a real gap in this version.

Decide which instances to start

GlobalConfigDictParser reads extra configuration, merges overrides, resolves inheritance and name substitutions, and composes the selected agent. It checks missing values and component pairings, then fills in defaults, addresses, and ports. This catches configuration errors before creating runtime resources.

gym env resolve --config … shows the resolved configuration. It reads configuration only; it does not test model access or run tasks.

RUNHELPER → HEAD SERVER

The parent process sets up the run

RunHelper.start() sets up observability, initializes or connects to Ray, then starts the Head Server in a thread. Head serves the full configuration, the instance list, and liveness and readiness endpoints.

Head is not a request gateway. Model requests do not pass through it. Child processes started by Gym use the configuration passed in by the parent. Other clients can fetch configuration from Head, then contact each service directly at its instance address.

RunHelper._start()HeadServerServerClient.load_from_global_config()

INSTANCE → SUBPROCESS

Find the implementation and run it in its own Python environment

RunHelper visits each service configuration with an entrypoint. It finds the component directory, prepares or reuses its venv, and uses that venv’s Python to run app.py. The parent passes the full configuration and current instance name to the child. It keeps the process handle for status checks and cleanup on exit.

Component lookup follows this order: extra search roots → current working directory → bundled package directory. A custom component can therefore override a built-in component with the same name. A slow first startup may be installing dependencies, rather than waiting for the model.

Directory lookup and startup commandChild processes and configuration injectioncomponent_search_roots()

APP.PY → FASTAPI → UVICORN

Turn a Python class into a reachable service

The entry point calls the concrete class’s run_webserver(). The shared implementation reads its configuration, creates the service object, and calls its setup_webserver() to register routes. It adds health checks and shared error, cancellation, and observability support. Finally, Uvicorn listens on the configured port. Chapter 05 walked through this code.

That is why many app.py files end with just one startup call. The shared library handles common web server work; the concrete class supplies routes and task-specific behavior.

SimpleServer.run_webserver()How a concrete class adds routes

PROCESS EXISTS ≠ TASK WORKS

Wait until Gym services and the model endpoint are reachable

The parent waits for all components to start, probes the configured upstream model endpoints, then marks Head as ready. If startup fails, it cleans up processes already started.

In this version, the endpoint probe accepts any HTTP response, including 401 and 404. It proves the address is reachable. It does not validate authentication, tool parsing, token output, or generation. After readiness, run a small real smoke test for your intended use.

COLLECTOR → ENVIRONMENT /RUN

Now individual tasks can run

The Collector prepares data rows and routes, limits concurrency, and sends tasks to the matching Environment’s /run. It then saves and summarizes results. The endpoint must match the data format. This tutorial follows the native format.

gym eval run runs the full pipeline by default: prepare data → start services → collect results → stop services. Add --no-serve to collect results using services that are already running. This flag does not fix an incorrect route in the configuration or data.

Control path: set up the run

CLI → configuration → RunHelper → Head + component processes → ready. This path decides which services start, which configuration they use, and who starts and stops them.

Request path: handle one task

Collector → Environment → Agent / Resources → model proxy / sandbox. This path handles the task’s input, waits, state, and output.

WHERE WORK RUNS

Container execution and cluster submission are separate layers

nemo_gym/sandbox/ provides create / connect / exec / stop operations for tasks. Providers map these operations to Docker, OpenSandbox, or other platforms. The calling component still decides which task owns which sandbox.

Why “sandbox provider” instead of “sandbox server”?

A provider is a replaceable implementation of capabilities. A server is a process that listens for requests. AsyncSandbox calls the provider’s create / connect / exec / stop methods. The Docker provider can use an SDK and daemon. The OpenSandbox provider connects to an OpenSandbox server over HTTP. A provider does not need its own Gym HTTP port.

The two names therefore refer to different layers: Resources Server → AsyncSandbox → OpenSandbox provider → OpenSandbox server → task container. Swapping the provider changes the execution backend. Resources still decides which task owns the sandbox and when to score and clean up.

Provider protocolAsyncSandbox API

nemo_gym/orchestration/ describes and submits a complete run: model services, compute resources, the benchmark driver, and job records. In this version, submit only registers a Slurm executor and is marked experimental. An extensible interface does not mean all cluster backends are already supported.

Look here when: container creation or connection fails, check sandbox. For GPU allocation, sbatch, or whole-run submission, check orchestration.

OBSERVATION ≠ TRAINING TOKENS

Observability and training support are separate requirements

telemetry/ handles traces, metrics, and other runtime observations. rollout_observability.py describes invocation, turn, and tool-call records. token_id_capture/ handles the exact tokens and call relationships needed for training.

Final text, usage reported by the harness, captured model calls, and token sequences for training are four different kinds of evidence. Ordinary evaluation does not require training token capture. Training support depends on whether the model and harness preserve enough information.

Core design: benefits and tradeoffs

These tradeoffs follow the boundaries in the source code. Components have not all migrated to the same pattern.

Design choiceWhat it enablesCost, and when a simpler option may help
Separate processes connected by HTTPAgents, models, and resources can be replaced and deployed independently, with separate dependencies. External harnesses can use common interfaces. One benchmark verifier can work with several models and harnesses.Serialization, networking, and partial failures add complexity. Logs are spread across services, so debugging follows the call chain. In-process functions may be easier to debug for small local experiments, but you must decide how components can be replaced.
YAML composition + instance referencesReuse one implementation in several combinations. Keep model parameters separate from benchmark rules.Merging, inheritance, and defaults can hide behavior. Read the resolved configuration. A hard-coded script is easier to follow, but duplicates configuration and makes experiments easier to drift apart.
Responses-style trajectories + a shared model interfaceMessages, function calls, and tool results have structure. The model proxy can link requests and trajectories in one place. Training paths can preserve token information.A flat result may not preserve an external harness’s subagents, context compression, or usage data. Adapters may also lose parameters, reasoning, or usage. Check each path and state which information is missing.
Environment manages execution; Resources scores itThe lifecycle can be reused across harnesses. Each harness no longer needs to reimplement seed / verify / cleanup. Task state and scoring assets have clear owners.This adds a service and protocol layer. Older run paths and new episodes coexist during migration, so check which path you use. Older agents can still use forwarding, but do not gain the new lifecycle guarantees.
The Agent borrows the Resources environmentYou can swap the harness while the benchmark retains control of the task image and scoring.Ownership, connection descriptors, retries, and close receipts require an extra protocol.
Score the patch again in a fresh environmentReduce the effect of temporary state, dependency changes, and background processes left by the agent.Extra startup cost. Patch export and file filtering can also fail.
Async I/O + concurrency limits at several layersMany tasks can share one control process while waiting for models, tools, or containers.Rate limits, cancellation, retries, and downstream capacity need to be designed together. Blocking calls stall the event loop. At high concurrency, resource leaks and queues cause more trouble.
Sandbox provider abstractionThe same task code can use different container platforms without depending on one deployment setup.Platforms differ. Check support for connect, PTYs, service ports, and TTL. A shared API does not remove runtime differences.
In-memory state + cleanup with time limitsA direct implementation that handles common failures and request retries.State is not automatically restored after a restart. Sharing state across workers and cleaning up after a process crash require separate solutions.

Evaluation and training: what is shared, and who updates the weights?

EVALUATION

Measure a fixed policy

Input tasks → run the agent → verify → save trajectories and scores → aggregate by sample validity. Gym coordinates environment interactions and measurement. Read success rates alongside failures, masks, coverage, and sampling conditions.

TRAINING

The training framework uses rollouts and rewards to update the policy

Gym provides environment interactions, trajectories, and rewards. Frameworks such as NeMo RL and VeRL handle optimization, gradients, and weight updates. The chosen training setup must also coordinate how updated weights reach the inference service.

On-policy RL that needs tokens and logprobs cannot use final text alone. Gym supports model responses with native token information. It also provides token capture and reconstruction for external harnesses. If the training call chain cannot be reconstructed reliably, keep the diagnostics and mask the sample. Retokenized text is not the original sampled trajectory.

train_data_utils.py processes data; it is not an optimizer. gym eval submit submits runs; it is not a training loop. reward_profile summarizes rewards; it does not improve the model. The Pro × Hermes recipe below is documented as an evaluation path. Gym’s RL support does not make that recipe ready for training.
