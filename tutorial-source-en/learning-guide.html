Look inside the same small example

The model asks for the weather tool. What gets sent next?

This is a handwritten example with only the key fields. It omits the other fields in a full request or response. We use Paris throughout to make the data easy to follow. The weather function returns a fixed message saying it is cold; it does not contact a weather website.

One item in the model's output

{"type":"function_call",
 "name":"get_weather",
 "call_id":"weather-1",
 "arguments":"{\"city\":\"Paris\"}"}

arguments is a JSON string. SimpleAgent decodes it with json.loads(), then sends the resulting object to Resources as the HTTP JSON body.

One item the Agent adds to the context

{"type":"function_call_output",
 "call_id":"weather-1",
 "output":"{\"city\":\"Paris\",\"weather_description\":\"The weather in Paris is cold.\"}"}

output holds the tool's response text. The matching call_id tells us which call it answers. The model sees this observation on its next turn.

Tool use needs three pieces: a declaration tells the model which tools exist, the Agent dispatches each call, and Resources runs the function. If you rename a tool, keep all three pieces in sync.

Try it: see what await does with a small Python script

You only need the Python 3.10+ standard library. Predict first: when you call an async function and get a coroutine object, does its body run yet? If four tasks each wait for 0.12 seconds, what happens when only two may enter at once?

python3 /path/to/download/async-mini-lab.py

The script runs four cases: await each coroutine in turn; create Tasks first, then await them in turn; allow two asynchronous waits at once; and call a blocking sleep inside an async function. After each case, it prints the full event array. Compare the start/end order and peak_in_flight, not just the elapsed time.

What to checkWhat to expect
Create a coroutine object onlyIts body has not run yet. Awaiting it starts the body.
Await each coroutine in turnA finishes before B starts. At most one operation holds a slot.
Call create_task first, then await each TaskAll four Tasks are already scheduled. Up to four operations are in flight. Awaiting them later does not undo that scheduling.
Schedule Tasks with a limit of 2At most two operations are in flight. Their waits can overlap.
Add time.sleep to concurrent codeIt blocks the event loop. Other Tasks cannot make progress during that sleep.

In flight means an operation has entered the controlled section and has not finished. This includes waiting time. It is not a count of CPU cores or threads. This experiment shows local scheduling; it cannot predict Gym or GPU throughput. The timeline above is a separate teaching simulation.

We ran this script with Python 3.13.14. Creating the coroutine did not enter its body. The four cases reached peak in-flight counts of 1, 4, 2, and 1. The timings describe this local experiment, not a Gym benchmark. We keep the script and its results separate so you can download it and repeat the check.

A habit for reading README files and docs

Follow each claim to code you can check

  1. Pin the version. Check which revision the command or page describes. latest may point to a release; it is not the same as main.
  2. Find the entry point. Follow a command to its CLI handler, or a URL to its route registration. Finding a function with the right name is only the start.
  3. Follow the branch that runs. Check configuration defaults, callers, and implementations. An interface may expose a method that your chosen provider does not support.
  4. Make a small check. Read the types and tests, then try an offline or single-service exercise. Valid configuration and a successful end-to-end model run need different evidence.
git rev-parse HEAD
rg -n 'def parse|env.yaml|OmegaConf.merge' nemo_gym/global_config.py
rg -n 'environment_server_routes|_native_episode_request_body' nemo_gym/rollout_collection.py
rg -n 'def disconnect|def stop|__aexit__' nemo_gym/sandbox

For example, check a claim about configuration order by following the list appends and OmegaConf.merge() in GlobalConfigDictParser.parse(). Even a docstring can lag behind the function body. Understand the branch that actually runs before using a command from the docs.

Find the last override before checking the run

In normal CLI use, values for the same key are merged in roughly this order. Included base files are read before the parent recipe. Among files at the same level, later files override earlier ones.

included base YAML → parent recipe → local env.yaml → CLI override

Inheritance, defaults, and reference validation follow. Where a file is found and which value overrides another are separate questions. Use gym env resolve to inspect the final configuration. It hides sensitive fields but does not test network connections.

Count it: how can 2 tasks × 2 samples produce 5 executions?

This is a handwritten identity example. The taskset demo-run is unique to this run, and each task has two planned samples. Task A's second sample left a retryable failure record, then ran once more during recovery.

task_idrollout_idattemptcapture_key
AA-r00A-r0
AA-r10A-r1
AA-r11A-r1-a1
BB-r00B-r0
BB-r10B-r1

The answer is 2 tasks, 4 planned samples, and 5 actual executions. A retry does not change num_repeats=2 to 3. Within the same live Hermes session, resending activation with the same capture key and request body can reuse the existing task without adding an attempt.

--resume reads the saved input snapshot, main results, and failure records to decide what still needs dispatching. A normal result with reward=0 still counts as returned. A low score alone is no reason to rerun it silently. A hard interruption may leave incomplete records, so also check result coverage.
