工具实现：只负责产生观察结果

async def get_weather(self, body: GetWeatherRequest) -> GetWeatherResponse:
    return GetWeatherResponse(city=body.city, weather_description=f"The weather in {body.city} is cold.")

Verifier：只负责定义“怎样算成功”

async def verify(self, body: BaseVerifyRequest) -> BaseVerifyResponse:
    reward = float(
        any(item.type == "function_call" and item.name == "get_weather" for item in body.response.output)
    )
    return BaseVerifyResponse(**body.model_dump(), reward=reward)

上面两段直接取自固定版本源码。注意这个教学 verifier 只检查“有没有调用名为 get_weather 的工具”，不检查城市对不对、天气真不真、最终回答好不好。所以这里的 reward=1 只能说明模型调用了这个工具。

把 SimpleAgent 的长函数缩成 12 行伪代码
# 教学伪代码：省略 cookies、校验、观测、错误处理与步数限制
async def run(task):
    await resources.seed_session(task)
    history = task.messages
    while True:
        reply = await model.responses(history, tools=task.tools)
        history += reply.output
        if not reply.tool_calls:
            break
        for call in reply.tool_calls:
            observation = await resources.tool(call.name, call.arguments)
            history += tool_output(call.id, observation)
    return await resources.verify(task, history)

await 表示“在这里等结果，同时让别的任务先跑”（第 04 章细讲）。同一道题内部的先后顺序不会变：拿到工具结果之后，模型才能看到它。SimpleAgent 对同一轮的多个工具调用也是逐个 await；多道题同时运行，是 Collector 那一层的并发。

小练习：想增加一个 get_humidity 工具，需要改哪里？
答案：工具声明、实现和评分要对齐

在任务的 tools 里声明名称和参数；在 Resources 里注册同名路由并实现处理函数；如果任务目标变了，还要更新 verifier、样例和测试。SimpleAgent 已经能按名字派发任意工具，通常不用改循环。如果只写了工具声明、没有对应的路由，模型仍然可能发起调用，但这个调用无法执行。

02

核心抽象：先约定“交什么”，再决定“怎么做”

只要协议不变，背后的实现就可以替换；谁拥有哪些状态，决定了组件能否安全地组合。

PYTHON / 实现侧

Base 定义契约，Simple 补上运行能力

BaseServer 是带配置和 HTTP 客户端的 Pydantic 对象；SimpleServer 在它之上加了 FastAPI / Uvicorn 的启动能力。Agent、Resources、Model 各自的基类再加上自己的路由和协议，具体的 app.py 只写业务逻辑。

这是按职责做的简化，不是严格的单继承树：源码里的 SimpleResourcesServer 等类用了多继承和 mixin。名字里的 “Simple” 也不代表它只做一件小事。

HTTP / 运行侧

跨进程传的是 JSON，不是 Python 对象

调用方把 Pydantic 数据转成 JSON，通过 HTTP 发出去；接收方按类型校验后再执行。self.server_client.post(...) 是一次网络请求，不是直接调用另一个对象的方法。

所以跨组件的调用可能遇到连接失败、响应丢失、重试和超时。后面 session 和 cleanup 的很多设计，都是为了应对这些情况。

接口输入 → 输出容易混淆的地方
模型 /v1/responses消息、工具声明、采样参数 → 模型输出项，以及可用的 usage / token 信息模型可以输出一个 function call，但那只是一段 JSON，工具并没有被执行。
Agent /v1/responses任务上下文 → 一次 activation 的完整输出，中间可能有多轮模型和工具调用路径和模型接口同名，只是为了格式兼容；它做的事比“问一次模型”多得多。
Resources 工具与 /verify工具参数 → 观察结果；任务 + 输出 / 状态 → reward 和诊断信息工具结果告诉 agent 发生了什么；verifier 判断任务是否完成。
原生 Environment /run带 task 和 episode 身份的请求 → 这次 episode 的结果，或结构化的失败Environment 负责流程和清理；怎么判分仍由 Resources 决定。
旧 Agent /runflat row → 带 response / reward 的结果还没迁移的 agent 自己依次调用 seed、responses 和 verify，没有原生 Environment 提供的那些保障。

原生请求分成 episode_id 和 task 两部分；task_input 里又分为给模型的 responses_create_params 和给 Resources 的 task_data。不同组件的 JSONL 额外字段并不完全相同，读数据时以具体组件为准。

任务身份和执行身份要分开。同一道题可以采样多条 rollout；某条 rollout 遇到基础设施错误时可能重新执行，产生多个 attempt。TaskId 标识题目，EpisodeId(rollout_id, attempt) 标识一次实际执行。分开它们，统计时才能分清自己数的是题数、样本数还是重试次数。后面各章提到身份时，都是指这里的定义。

reward=0 和“没测出结果”是两回事。
mask_sample 表示这个样本是否应该排除在质量统计之外；failure_kind 描述发生了什么，但不会自动决定是否 mask。类型只是提供了表达方式，具体 verifier 必须正确填写。第 11 章的 Pro 案例会指出这个版本里的一个实际缺口。

03

Serving：让程序一直在线、随时接请求

先分清谁是服务、谁是客户端，以及它们实际跑在哪台机器上。

普通脚本通常是“启动 → 做完一件事 → 退出”。服务进程启动后会一直监听一个端口：收到请求就运行对应的函数，再返回结果。比如 POST /verify 就是一个 HTTP 请求：host 和端口决定找哪个服务，路径决定调用它的哪个入口，JSON body 携带这次调用的数据。

GYM SERVING

把 Python 组件变成 HTTP 服务

FastAPI 把 URL 绑定到 Python 函数，Uvicorn 负责监听端口、处理网络连接。Agent Server 可能只跑控制逻辑；Resources Server 的大部分时间可能都在等容器和测试。

gym env start 会启动配置好的一组 Gym 服务。服务启动成功，不代表任务已经跑完。

MODEL SERVING

真正把权重放到 GPU 上生成 token

vLLM、NIM 等推理服务负责加载模型权重、管理显存和请求队列、执行推理。Gym 的 Model Server（模型代理）位于调用方和推理服务之间，负责协议转换、请求参数和轨迹关联。

如果已经有模型 endpoint，Gym 直接连接它。启动 Gym 的模型代理，不会自动分配 GPU、提交 Slurm 作业或加载 checkpoint。

A · 控制侧：可能是工作站，也可能是集群上的控制进程
控制侧通过 provider 的 create / connect / exec / stop 操作任务环境 ↓
B · 任务 sandbox：本地 Docker 或远程 provider；不一定需要 GPU
Hermes runner ── HTTP 模型请求 → Gym 模型代理 ── HTTP → 推理后端
最常见的网络误会：localhost 指的是“我自己”。

04

Async：这道题在等，别的题可以继续

等网络、等模型、等容器的时间，往往比 Python 真正计算的时间长得多。

可以把 event loop 想成一个调度员：协程运行到一个还没完成的异步 I/O await 时，就把执行权让出来；结果回来后，再从原处继续。同一个协程内部的先后顺序不会变：必须先创建 sandbox 才能连接；必须先拿到模型的工具调用，才能执行这个工具。

交互实验 · 4 个请求

换一种等待方式，看看时间线

教学模拟，非实测

每个请求：本地处理 0.25 s → 等待外部 I/O 3 s → 本地处理 0.25 s。假设外部 I/O 可以互不影响地并发，但同一个 event loop 上的本地处理仍然是串行的。没有模拟 GPU batching、网络拥塞或重试。

本地处理异步 I/O 等待阻塞调度线程排队，未轮到执行
四个请求全部完成
固定刻度 0–14 秒
方便比较三种模式

并发不等于“全部并行计算”

同一个 Python event loop 在同一时刻只执行一个 task 的 Python 代码。能重叠的是等待；模型服务器如何 batch、多块 GPU 如何并行，是另一层的调度。

在 async def 里直接调用同步的网络请求或 time.sleep()，仍然会卡住这个 event loop。把同步函数放进 asyncio.to_thread() 可以避免卡住它，但取消等待并不会自动终止那个线程或远程进程。

Semaphore：限制同时进行的数量

允许同时处理两题，不代表有两块 GPU，也不保证同时存在的容器最多两个。限流放在哪一层，就只限制那一层。

在这个配方里，Hermes（第 09 章案例中的 agent）的 sem 只限制 activation；Resources seed 和 agent seed 都发生在它之前，不受它限制。要控制整个 episode 的资源规模，要看 Collector 和 Environment 的准入限制。

不会。第二个调用要等第一个返回后才开始。要让它们重叠，需要先把多个 task 调度起来，再统一等待，并限制同时执行的数量，避免压垮下游。async 允许任务在等待时让出执行机会，但不会替你判断哪些业务步骤可以并发。这里的 A/B 是刚创建的新协程。如果先用 create_task 调度 A/B，再逐个 await，它们仍可交错执行。下方小实验会对比这两种写法。

"""A standard-library-only async lesson. No HTTP, Gym, GPU or subprocesses.

Run: python3 async-mini-lab.py
Predict peak_in_flight first: sequential=1, scheduled=4, bounded=2, blocking=1.
The counter includes waiting operations; it does not count CPUs or threads.
Elapsed seconds are illustrative measurements, never benchmark assertions.
"""

import asyncio
import json
import time


async def run_case(mode: str) -> dict[str, object]:
    in_flight = 0
    peak_in_flight = 0
    events: list[str] = []
    semaphore = asyncio.Semaphore(2)

    async def operation(name: str) -> None:
        nonlocal in_flight, peak_in_flight
        in_flight += 1
        peak_in_flight = max(peak_in_flight, in_flight)
        events.append(f"{name}:start")
        try:
            if mode == "blocking":
                time.sleep(0.12)  # Deliberate anti-example: occupies the loop's thread.
            else:
                await asyncio.sleep(0.12)  # Simulates waiting; no actual network I/O.
        finally:
            events.append(f"{name}:end")
            in_flight -= 1

    async def bounded(name: str) -> None:
        async with semaphore:
            await operation(name)

    started = time.perf_counter()
    if mode == "sequential":
        for name in "ABCD":
            await operation(name)
    elif mode == "scheduled":
        tasks = [asyncio.create_task(operation(name)) for name in "ABCD"]
        for task in tasks:
            await task  # Already scheduled: these await statements do not serialize starts.
    else:
        worker = bounded if mode == "bounded" else operation
        await asyncio.gather(*(worker(name) for name in "ABCD"))
    return {
        "mode": mode,
        "peak_in_flight": peak_in_flight,
        "elapsed_seconds": round(time.perf_counter() - started, 3),
        "events": events,
    }


async def main() -> None:
    entered: list[bool] = []

    async def probe() -> None:
        entered.append(True)

    coroutine = probe()  # Creates a coroutine object, without scheduling its body.
    await asyncio.sleep(0)
    print(json.dumps({"created_coroutine_has_started": bool(entered)}))
    await coroutine  # Consume it, so no unawaited-coroutine warning remains.
    for mode in ("sequential", "scheduled", "bounded", "blocking"):
        print(json.dumps(await run_case(mode)))


if __name__ == "__main__":
    asyncio.run(main())

机制解决什么问题不能据此推断
async / await一个进程在等待 I/O 时，让其他协程继续运行不会因此多出 GPU 或容器容量。

# SPDX-FileCopyrightText: Copyright (c) 2026 NVIDIA CORPORATION & AFFILIATES. All rights reserved.
# SPDX-License-Identifier: Apache-2.0
"""Prepare native Collector inputs; this tutorial helper makes no HTTP calls."""

import argparse
import json
from pathlib import Path
from uuid import uuid4

from nemo_gym.episode_types import MaterializedTask, TaskId
from nemo_gym.single_agent_turn_types import SingleAgentTurnTaskInput


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("input", type=Path)
    parser.add_argument("output_dir", type=Path, help="A new run directory; existing paths are refused")
    parser.add_argument("--limit", type=int, default=1, help="Number of tasks; 0 selects all")
    args = parser.parse_args()
    if args.limit < 0:
        parser.error("--limit must be nonnegative")
    taskset = f"swebench_pro:{uuid4().hex}"
    tasks = []
    seen = set()
    with args.input.open() as source:
        for line in source:
            row = json.loads(line)
            task = MaterializedTask[SingleAgentTurnTaskInput](
                task_id=TaskId(taskset=taskset, task_id=row["instance_id"]),
                task_input=SingleAgentTurnTaskInput(
                    responses_create_params=row["responses_create_params"],
                    task_data={
                        k: v for k, v in row.items()
                        if k not in {"responses_create_params", "agent_ref", "task_source", "skills_ref"}
                        and not k.startswith("_ng_")
                    },
                ),
            )
            if task.task_id.task_id in seen:
                raise ValueError(f"Duplicate instance_id: {task.task_id.task_id}")
            seen.add(task.task_id.task_id)
            tasks.append(task.model_dump(mode="json", exclude_unset=True))
            if args.limit and len(tasks) >= args.limit:
                break
    if not tasks:
        raise ValueError("Input contains no tasks")
    args.output_dir.mkdir(parents=True, exist_ok=False)
    with (args.output_dir / "tasks.jsonl").open("x") as output:
        for task in tasks:
            output.write(json.dumps(task) + "\n")
    # JSON is valid YAML; quoting the run-unique taskset avoids YAML key ambiguity.
    with (args.output_dir / "routing.yaml").open("x") as output:
        json.dump({
            "environment_routing_mode": "taskset",
            "environment_server_routes": {taskset: "single_agent_turn"},
        }, output, indent=2)
        output.write("\n")
    print(f"Prepared {len(tasks)} task(s) in {args.output_dir}; taskset={taskset}")


if __name__ == "__main__":
    main()

以下是从源码边界总结出的取舍。并不是所有组件都已经迁移到同一种模式。

设计选择换来的能力代价，以及何时用更简单的方案
组件分进程，通过 HTTP 交互Agent、模型、资源可以独立替换和部署，依赖互相隔离；外部 harness 能通过通用接口接入；同一个 benchmark verifier 可以搭配不同的模型和 harness。数据要经过序列化和网络传输，还可能只有部分服务成功。日志也分散在多个服务里，排错时需要沿调用链查找。单机的小实验用进程内函数组合更好调试，但要自己划清可替换的边界。
YAML 组合 + 实例引用同一份实现可以组成多种搭配；模型参数和 benchmark 规则分开维护。合并、继承和默认值会影响最终行为，不能只看单个文件，要检查合并后的配置（resolved config）。写死的脚本更直观，但配置会重复，实验之间更容易漂移。
Responses 风格的轨迹 + 统一模型入口消息、函数调用、工具返回都有结构；模型代理能集中关联请求和轨迹，训练路径可以保留 token 信息。外部 harness 的子 agent、上下文压缩和自带的 usage，不一定能无损放进一个扁平结果；参数、thinking、usage 也可能在适配中丢失。需要逐条路径核对，缺失的信息要明确标出。
Environment 编排，Resources 判分生命周期独立于具体 harness，可以复用，不用每个 harness 再写一遍 seed / verify / cleanup；任务状态和评分资产有明确的所有者。多了一层服务和协议。迁移期间旧 run 和新 episode 并存，要分清走的是哪条路径；旧 agent 可以继续走转发路径，但不具备新生命周期的保障。
Agent 借用 Resources 的环境harness 可以换，任务镜像和评分逻辑仍由 benchmark 控制。所有权、连接 descriptor、重试和 close 返回记录构成了一套额外的协议。
在全新环境里重新评分 patch减少 agent 留下的临时状态、依赖改动和后台进程对评分的影响。额外的启动成本；patch 导出和文件过滤本身也可能出错。
异步 I/O + 多层并发限制大量任务在等模型、工具、容器时，可以共用一个控制进程。限流、取消、重试和下游容量必须一起设计。阻塞调用会卡住整个 event loop，高并发也会加重资源泄漏和排队。
Sandbox provider 抽象同一套任务代码可以接不同的容器平台，业务代码不必绑定某种部署方式。各平台能力不同，connect、PTY、服务端口、TTL 都要按能力检查。统一的 API 不会消除运行时的差异。

生命周期：结束、重试和评分是三件事

会话（session）管理和清理（cleanup）的代码比较长，因为它们要应对远程系统中的失败、超时和响应丢失。

重试时，身份怎么用

回顾第 02 章：TaskId 是“哪道题”，rollout_id 是一次逻辑采样，attempt 区分恢复后的实际执行。对应的 capture_key 形如 r42、r42-a1……

在同一个仍存活的 Hermes session 内，同一 capture key、同一请求正文再次调用 activation，会加入已有的 state.task；修改正文会得到 409。这个保证不覆盖整个 Environment /run 的重放，也不覆盖服务进程重启。恢复时先检查原执行的状态和 Collector 记录，再决定新的 attempt。

Cookie 和 descriptor 各管什么

session cookie 让 Resources 找回服务器上这道题的状态。SandboxAccess 携带 provider 引用、序列化的连接 descriptor 和 workdir=/app，让 Agent 能连到同一个 sandbox。

descriptor 只是连接信息：不会复制容器，也不转移生命周期的所有权。借用方用 disconnect()，拥有方用 stop()。

为什么一定要先关 agent，再验证？

设想 shell 工具启动了一个后台进程：模型已经回复“我完成了”，后台进程却还在写文件。这时导出 patch，就会和正在进行的修改相互竞争，甚至污染评分。所以新路径先拿到 Agent 的 close 返回记录、确认 runner 已经清理，再让 Resources 提取 patch；提取后停掉任务 sandbox，评分时用全新的 sandbox。HTTP 请求返回了，不代表远程的进程树已经结束。

情况当前的处理原因
seed 的响应丢了调用方先生成 session ID、登记 cleanup，再发 seed即使没收到成功响应，也知道要关闭哪个远程 session
同一个 activation 被重试请求绑定到 state.task：相同请求加入原任务，不同请求返回 409避免启动第二个 worker 同时修改同一个仓库
Agent close 无法确认返回 cleanup 阶段的失败，保留部分结果，跳过 verify先确认 agent 不会继续修改文件
模型做完了，但评分器断网在预算内新建 grader 有限重试；检查最终的 completed / error区分基础设施失败和真实的测试失败；不会因为评分失败而重新生成答案
verify 被重复调用typed session 的任务 sandbox 已经用过，直接报错不能把第二次“没有 patch”当成正常的 0 分；注意并不是所有接口都幂等
评分成功后 Resources close 出错最后收尾时有限重试并记录错误，不覆盖已经得到的评分保留评分证据，同时单独报告清理问题
进程或主机突然死亡本地 finally 不一定能执行，需要依靠 provider 的 TTL / lease 或外部回收CleanupContext 不是持久化的工作流引擎，也不会无限重试

超时限制不止一个数字

请求 / 命令

一次等待多久

模型 HTTP timeout 和 terminal 命令 timeout，分别限制一次模型请求和一次 shell 命令。把它们调大，修不好错误的地址。

Runner / Episode

整个过程多久

runner 限制 Hermes 循环的时长；episode 还包括 seed、关闭 agent 和 verify。外层预算太短，会在内层完成之前就取消任务。

Cleanup / TTL

停止后还留多久

cleanup 有一个独立于 episode deadline 的时间上限。sandbox 的租约要覆盖它实际存活的时间；超时返回，不代表容器马上消失。

这个配方继承的部分默认值：Hermes 30 轮、terminal 60 s、runner 21600 s；Environment episode 21600 s、cleanup 180 s；Pro 测试命令 3600 s、单次验证 attempt 1200 s、总计 2700 s。注意：单次验证 attempt（1200 s）会比测试命令的上限（3600 s）先到期。这些值的作用范围不同，不能简单相加得到总时长；它们也没有针对你的目标任务验证过。

为什么不能随便增加 FastAPI workers？

一个 worker 是一个服务进程，不是一个协程。这个版本的 Pro session 映射保存在进程内的字典里，所以 num_workers != 1 会直接报错；Hermes sessions 同样要求单 worker。请求一旦被分到另一个进程，就找不到原进程里的 session。

Environment 本身支持多个 worker，但每个 worker 的 semaphore 和准入队列是各自独立的，整体名额约等于 workers × max_concurrent_episodes。加 worker 也绕不开有状态下游的限制。应该先调 Collector 和 episode 的并发，观察下游容量，再考虑跨进程的状态或路由设计。

"""Prepare one typed request offline; no serving, HTTP calls, or model execution."""

import argparse
import json
from pathlib import Path
from uuid import uuid4

from nemo_gym.single_agent_turn_types import SingleAgentTurnRequest


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("input", type=Path)
    parser.add_argument("output", type=Path)
    parser.add_argument("--row", type=int, default=0, help="Zero-based JSONL line index")
    parser.add_argument("--taskset", default=None, help="Keep fixed for one run")
    parser.add_argument("--rollout-id", default=None, help="Keep fixed across attempts of one rollout")
    parser.add_argument("--attempt", type=int, default=0)
    args = parser.parse_args()
    if args.row < 0:
        parser.error("--row must be non-negative")
    with args.input.open() as stream:
        row = next((json.loads(line) for i, line in enumerate(stream) if i == args.row), None)
    if row is None:
        parser.error("--row is outside the input file")
    # Routing belongs to the caller/config. Resources receives the task fields.
    excluded = {"responses_create_params", "agent_ref", "task_source", "skills_ref"}
    request = SingleAgentTurnRequest.model_validate({
        "episode_id": {
            "rollout_id": args.rollout_id or f"tutorial-{uuid4().hex}",
            "attempt": args.attempt,
        },
        "task": {
            "task_id": {
                "taskset": args.taskset or f"swebench_pro:tutorial-{uuid4().hex}",
                "task_id": row["instance_id"],
            },
            "task_input": {
                "responses_create_params": row["responses_create_params"],
                "task_data": {
                    key: value for key, value in row.items()
                    if key not in excluded and not key.startswith("_ng_")
                },
            },
        },
    })
    # Refuse to overwrite a previously materialized identity/request.
    with args.output.open("x") as stream:
        stream.write(request.model_dump_json(indent=2) + "\n")
    print(f"Prepared {args.output}; no model call was made")


if __name__ == "__main__":
    main()

taskset 标识这次运行的任务集合，task_id 标识题目；rollout_id 和 attempt 的含义见第 02 章。脚本默认每次生成新的身份：同一次运行的多道题应传入相同的 --taskset；同一个 rollout 重试时保留 --rollout-id，并把 --attempt 加一。Environment /run 不会为整个调用做持久化去重，所以不要把重发 HTTP 当作没有代价的重试。

用仓库问题检查理解

① 看到 ResourcesServer，是不是就意味着有容器？

不是。它管理任务资源和验证；天气例子只返回一个 Python 对象。是否需要 sandbox，由具体任务决定。

② 实例名、实现目录名、上游模型名有什么区别？

实例名是这次配置中的节点名；实现目录名决定加载哪份代码；上游模型名是发给推理服务的模型标识。例如 policy_model 可以是一个 vllm_model 代理的实例名。

③ 为什么只读 nemo_gym/ 不能理解某个 benchmark？

公共库提供可组合的机制，具体的任务数据、工具和评分规则在组件和配方里。反过来，只读某个 app.py，也会漏掉启动、路由和收集这些公共行为。

④ 所有 /run 都走同一个基类生命周期吗？

不是。原生 Environment 用 BaseEnvironmentServer 的 run_request 包住 run；legacy_agent 自己注册一个转发路由，把请求交回旧的 Agent.run。要看具体的 setup_webserver，才能确认走的是哪条路。

用 benchmark 问题检查理解

① 模型说“已修复”，但 patch 没有变化，应该信谁？

信实际状态和 verifier。SWE-Pro 从任务 sandbox 的 git diff 导出候选 patch，再在干净环境里评分；模型的自然语言说明不等于测试通过。

② async 并发从 2 调到 32，为什么可能反而更慢？

模型队列、容器名额、网络连接池或测试资源会先饱和，增加等待和超时。协程可以同时等更多请求，但不会凭空增加下游容量。应该先测各阶段的延迟和资源，再调整限制。

③ Agent 关闭了借来的 sandbox，为什么是 bug？

Resources 还要从里面提取仓库的修改。Agent 应该先清理自己启动的进程，再 disconnect；任务 sandbox 归 Resources 所有，导出 patch 之后才由它 stop。

④ 第 13 章的原生入口示例和第 11 章的真实运行，验证范围相同吗？

不同。两者都走 Environment → hermes_agent native sessions，但真实运行的外层仍经过 flat-row 适配器，而第 13 章的配置直接接收 typed 请求；两者的源码版本和预算也不同。内部生命周期已经被真实运行验证过，但这个新入口组合还没有用模型端到端跑过。

把三种“再试一次”分别记账

记录里观察到什么
