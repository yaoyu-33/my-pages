02

核心抽象：组件先约定“交什么”，再决定“怎么做”

同一种协议背后可以换实现；边界和所有权决定能否安全组合。

PYTHON / 实现侧

Base 定义契约，Simple 提供常用运行能力

BaseServer 是带配置和客户端的 Pydantic 对象；SimpleServer 增加 FastAPI / Uvicorn 的公共启动能力。Agent、Resources、Model 的基类再补相应路由和协议；具体 app.py 实现业务。

这是职责概括，不是严格单继承树。源码里的 SimpleResourcesServer 等使用多继承和 mixin；“Simple” 也不代表该类只做一件小事。

HTTP / 运行侧

跨进程交的是 JSON，不是 Python 对象引用

调用方把 Pydantic 数据序列化为 JSON，经 HTTP 发送；被调用方按类型校验再执行。self.server_client.post(...) 是网络调用，不是直接调用另一实例的 Python 方法。

因此会出现连接失败、响应丢失、重试、超时；程序内的一次调用成功返回，不再是唯一可能的结果。后面的 session / cleanup 设计就是为这些边界服务。

契约输入 → 输出不要混淆
模型 /v1/responses消息、工具声明、sampling 设置 → 模型输出项和可用的 usage / token 信息模型可以提出 function call；生成这个 JSON 本身还没有执行工具。
Agent /v1/responses任务上下文 → 完整 activation 的输出，内部可包含多轮模型与工具调用同名 endpoint 表达兼容外形，不代表和一次模型推理具有相同执行范围。
Resources 工具与 /verify工具参数 → 观察；任务 + response / 状态 → reward 与验证诊断工具观察告诉 agent 世界发生了什么；verifier 判断任务是否完成。
原生 Environment /run带 task / episode 身份的请求 → 一次 episode 的结果或结构化失败负责流程和清理；具体任务怎样判分仍由 Resources 定义。
旧 Agent /runflat row → 带 response / reward 的验证结果还没有迁移的 agent 自己串起 seed、responses 和 verify。不能套用原生 Environment 的所有限制。

03

Serving：让一段程序随时能接请求

先分清谁是服务、谁是客户端，和它们实际在哪台机器上。

普通脚本往往“启动 → 做完一件事 → 退出”。服务进程启动后持续监听一个端口，收到请求就运行对应函数，再返回结果。比如 POST /verify 是一个 HTTP 请求：发到哪个 host/port 决定找哪一个服务，路径决定调用它的哪个入口，JSON body 携带这次调用的数据。

GYM SERVING

把 Python 组件变成 HTTP 服务

FastAPI 把 URL 绑定到 Python 函数，Uvicorn 负责监听和处理网络连接。Agent Server 可以只运行控制逻辑；Resources Server 可以主要是在等待容器和测试。

gym env start 启动组合好的 Gym 服务。服务启动成功，不代表已经跑完一题。

MODEL SERVING

真正把权重放到 GPU 上生成 token

vLLM / NIM 等推理服务加载模型权重，管理显存和请求队列，执行推理。Gym 的 Model Server 在它前面负责 API 适配、请求参数和轨迹关联。

已有模型 endpoint 时，Gym 连接它；启动 Gym 的模型代理不等于自动分配 GPU、提交 Slurm 作业或加载 checkpoint。

04

Async：这道题在等，别的题可以继续

等待网络、模型和容器，往往比本地 Python 真正在计算的时间长。

把 event loop 想成一个调度员。协程跑到尚未完成的异步 I/O await 时，让出执行权；有结果后再从原处继续。同一个协程的先后依赖依然存在：必须先创建 sandbox，才能连接；必须先得到模型的工具调用，才能执行该工具。

交互实验 · 4 个请求

改变等待方式，看看时间线

教学模拟，非实测

每个请求：本地处理 0.25 s → 外部 I/O 等待 3 s → 本地处理 0.25 s。外部假设可以独立并发，单 event loop 的本地处理仍串行；未模拟 GPU batching、网络拥塞或重试。

本地处理异步 I/O 等待阻塞调度线程未获执行机会
四个请求全部完成
固定刻度 0–14 秒
方便比较三种模式

并发不是“全部并行计算”

同一 Python event loop 在一个时刻只执行一个 task 的 Python 代码。等待可以重叠；模型服务器怎样 batch、多块 GPU 怎样并行，是另一层调度。

async def 内直接调用同步网络请求或 time.sleep()，仍会挡住这个 event loop。把同步函数移到 asyncio.to_thread() 可避免挡住它，但取消等待不会自动杀掉线程或远程进程。

Semaphore 是限流的“名额”

允许同时在途两题，并不意味着有两个 GPU，也不保证已经创建的容器最多只有两个。限流放在哪里，限制的范围就在哪里。

本配方里 Hermes 的 sem 限制 activation；Resources 和 agent seed 发生在它之前。控制整条 episode 的资源规模，要看 Collector 和 Environment 的准入限制。

            elif body != state.activation_request:
                raise HTTPException(409, "Hermes sandbox sessions support one activation; retry the same request")
            assert state.task is not None
            # A disconnected HTTP waiter must not cancel the shared activation. Session close
            # owns cancellation; identical retries join this task or replay its result/error.
            return (await asyncio.shield(state.task)).model_copy(deep=True)
        if not isinstance(rollout_id, str):
            return await self._create_response(body)
        episode = await self._create_episode(body, rollout_id=rollout_id)
        return episode.response.model_copy(
            update={_INTERNAL_OBSERVATIONS_KEY: episode.observations.model_dump(mode="json")}
        )

state.task 保存这次 activation。同样的 HTTP 请求重试会等待同一份结果。shield 让一个断开的 HTTP 等待者不要连带取消共享的 activation；真正的停止由 session close 管理。它不是“永不取消”，更不是无限后台运行的保证。

管理的难点：结束、重试和评分不是同一件事

看起来“啰嗦”的 session 和 cleanup 代码，是在处理远程系统的不确定性。

任务身份与尝试身份分开

TaskId 是“哪道题”；rollout_id 是一个逻辑尝试；attempt 区分恢复后的物理执行。相应 capture_key 会是 r42、r42-a1……

相同 HTTP 请求的传输重试，应该加入同一个 activation；明确的新 attempt 才创建新任务环境、留下新证据。否则一次网络抖动就会悄悄多采样一次模型。

Cookie 和 descriptor 各管什么

session cookie 帮 Resources 找到服务器里的任务状态。SandboxAccess 携带 provider 引用、序列化连接 descriptor 和 workdir=/app，供 Agent 连接同一个 sandbox。

descriptor 是连接信息，不会复制容器，也不转让生命周期所有权。借用方用 disconnect()；拥有者用 stop()。

为什么一定要先关 agent，再验证？

假设 shell 工具启动了后台进程，模型回复“我完成了”，但后台还在写文件。此时导出 patch 会和修改竞争，甚至污染评分。新路径先获取 Agent close receipt、确认 runner 清理，再让 Resources 提取 patch；提取后停止任务 sandbox，评分用全新 sandbox。“HTTP 请求结束”不等于“远程进程树已结束”。

情形当前设计的处理为什么
seed 的响应丢了调用方先生成 session ID 并注册 cleanup，再发 seed即使没拿到成功响应，也知道该关闭哪个远程 session
同一次 activation 被重试固定请求绑定到 state.task；相同请求加入原任务，不同请求返回 409避免启动第二个修改同一仓库的 worker
Agent close 无法确认返回 cleanup-stage failure，保留 partial response，跳过 verify先保证文件不会继续被 agent 改写
模型完成但评分器断网新建 grader 的有限重试；检查最终 completed / error基础设施失败和有效测试失败分开；不因评分失败重新生成答案
verify 被重复调用typed session 的 task sandbox 已被消费则报错不能将第二次“没有 patch”包装成正常 0 分；这不是所有 API 都幂等
评分成功后 Resources close 出错最终 unwind 有限重试并记录错误，不覆盖已经拿到的 verdict保留评分证据；仍要单独报告清理问题
进程 / 主机突然死亡本地 finally 不会可靠执行；需要 provider TTL / lease / 外部回收CleanupContext 不是持久化工作流引擎，也没有无限后台重试

Timeout 不是一个万能的数字

请求 / 命令

一次等待多久

模型 HTTP timeout 和 terminal command timeout，分别约束一次模型请求、一次 shell 命令。调大它们不能修复坏地址。

Runner / Episode

整段过程多久

runner 限制 Hermes 循环；episode 还包含 seed、agent close 和 verify。最外层预算太短，会在内层完成前取消任务。

Cleanup / TTL

停止后还留多少时间

cleanup 在 episode deadline 之外有独立上限。sandbox 的租约要覆盖其实际存活阶段；超时返回不意味着容器立即消失。

本配方继承的部分默认值：Hermes 30 turns、terminal 60 s、runner 21600 s；Environment episode 21600 s、cleanup 180 s；Pro test command 3600 s、verification attempt 1200 s、total 2700 s。attempt 外层会先于 3600 s 内层测试截止。这些值的 scope 不同，不能相加就得到精确总时长，也不是经过你目标任务验证的基准预算。

为什么不能随便增加 FastAPI workers？

一个 worker 是一个服务进程；它不是一个 coroutine。此版本的 Pro session 映射保存在进程内字典，num_workers != 1 会显式报错。Hermes sessions 同样要求一个 worker。请求被分发到别的进程时，并不会自动得到原进程内的 session。

Environment 本身支持多个 worker，但每个 worker 的 semaphore 和准入队列各自独立，部署总名额大约是 workers × max_concurrent_episodes。增加它并不能绕过有状态下游的约束。先调 Collector/episode 并发并观察下游容量，之后再设计跨进程状态或路由。

    找 session ID、capture_key、state.task。解释同样请求重试为何不会重复修改仓库。
  4. 读 _run_sandbox_episode()

    把 admission、deadline、finally、LIFO cleanup 与“主机突然死亡”的情况逐一对照。

先用 repo 问题检查理解

① 看到 ResourcesServer，是不是就意味着有容器？

不是。它管理任务资源与验证；天气例子只返回 Python 对象。是否需要 sandbox 由具体任务决定。

② instance name、实现目录名、上游模型名有什么区别？

instance name 是本次配置中的节点标识；实现目录名决定加载哪份代码；上游模型名是发送给推理 provider 的模型标识。例如 policy_model 可以是一台 vllm_model 代理的实例名。

③ 为什么不能只读 nemo_gym/ 就理解某个 benchmark？

公共库提供可组合机制，具体任务数据、工具和评分规则在组件 / 配方中。反过来，只读某个 app.py 也会漏掉启动、路由与收集的公共行为。

④ 所有 /run 都执行同一个基类生命周期吗？

不是。原生 Environment 用 BaseEnvironmentServer 的 run_request 包住 run；legacy_agent 自己注册透传路由，把请求交回旧 Agent.run。读具体 setup_webserver 才能确认走哪条路。

再用 benchmark 问题检查理解

① 模型说“已修复”，但 patch 没有变化，应该信谁？

信实际状态和 verifier。SWE-Pro 通过任务 sandbox 的 git diff 导出候选 patch，再在干净环境评分；自然语言承诺不构成测试通过。

② async 并发从 2 调到 32，为什么可能更慢？

模型队列、容器名额、网络连接池或测试资源先饱和，会增加等待和超时。协程能多等一些请求，但不会创造下游容量。先测各阶段延迟和资源，再调整限制。

③ Agent 关闭了借来的 sandbox，为什么是 bug？

Resources 还要提取仓库修改。Agent 应先清理自己启动的进程，再 disconnect；Resources 拥有 task sandbox，导出后才 stop。

④ 当前 native 配方和成功样本是不是同一条执行路线？

不是。教程当前源码使用 Environment → hermes_agent native sessions；真实成功样本来自旧 hermes_sandboxed_agent.run()。两者复用 Pro verifier 的思路，但 orchestrator、runtime pin、toolset 和异常处理不同。旧成功不能替新路线做端到端验收。
