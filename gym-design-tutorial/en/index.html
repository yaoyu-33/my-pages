Gym’s basic idea: It breaks an agent's work in a task environment into components you can combine. The shared library defines protocols and runtime behavior. Individual components handle the model, harness, task state, and scoring. YAML selects the combination for each run.

Terms you will see throughout

Keep these names in mind as you read. They match the names you can search for in the code.

Task · TaskIdOne problem to solve. taskset + task_id identifies the task set and the task within it.
rollout · attemptA rollout is one sample for a task. Each execution of that sample is an attempt, including reruns after infrastructure failures. The rollout ID and attempt number form an EpisodeId.
episodeOne attempt's full lifecycle: setup, execution, scoring, and cleanup.
CollectorThe client program that reads tasks in batches, sends requests, and saves results.
harness · AgentThe program that runs the model ↔ tool loop, such as SimpleAgent or Hermes. An Agent Server exposes it as a Gym service.
Model Server (model proxy)A Gym service that forwards model requests, adapts protocols, and records calls. Actual inference runs in a backend such as vLLM or NIM.
Resources · verifierResources manages task state and tools. Its verifier scores the task and returns a reward.
EnvironmentThe service that coordinates an episode. It calls Resources and Agent in order and handles cleanup.
seed · sessionSeed prepares state before a task starts. A session holds that task's state on the server. A cookie or session ID retrieves it.
activationEnvironment asks Agent to complete a task through one /v1/responses call. That call can contain many model and tool turns.
sandboxA shared interface for an execution environment. The provider determines its isolation. This tutorial uses a container backend: task container A serves the agent, and clean grading container B runs verification.
Typed request · flat row · smoke runA typed request separates task identity from episode identity. A flat row is the older format with fields at the top level of a JSONL row. A smoke run uses one or two real tasks to check that the components work together.

SimpleAgent’s long function, reduced to 12 lines of pseudocode
# Teaching pseudocode: cookies, validation, tracing, errors, and step limits omitted
async def run(task):
    await resources.seed_session(task)
    history = task.messages
    while True:
        reply = await model.responses(history, tools=task.tools)
        history += reply.output
        if not reply.tool_calls:
            break
        for call in reply.tool_calls:
            observation = await resources.tool(call.name, call.arguments)
            history += tool_output(call.id, observation)
    return await resources.verify(task, history)

await means “wait here for the result, while allowing other tasks to run” (more in Chapter 04). Steps within one task still have an order: the model can only see a tool result after it arrives. SimpleAgent also awaits tool calls from the same model turn one at a time. The Collector provides concurrency across separate tasks.

02

Core abstractions: agree on the contract, then choose the implementation

A stable protocol lets you swap implementations. Clear state ownership lets components work together safely.

PYTHON / IMPLEMENTATION

Base defines the contract; Simple adds server support

BaseServer is a Pydantic object with configuration and an HTTP client. SimpleServer adds FastAPI / Uvicorn startup support. The Agent, Resources, and Model base classes add their routes and protocols. Each concrete app.py then implements the task-specific behavior.

This is a simplified view of responsibilities, not a strict single-inheritance tree. Classes such as SimpleResourcesServer use multiple inheritance and mixins. “Simple” in a class name does not mean the class does only one small thing.

HTTP / RUNTIME

Processes exchange JSON, not Python objects

The caller serializes Pydantic data as JSON and sends it over HTTP. The receiver validates the data before handling it. self.server_client.post(...) sends a network request; it does not call a method on another Python object.

Calls between components can fail to connect, lose a response, retry, or time out. Many of the session and cleanup rules below address these cases.

Keep task identity separate from execution identity. One task can produce several sampled rollouts. An infrastructure failure may cause a rollout to run again, creating several attempts. 03

Serving: keep a program ready to accept requests

Identify the services, their clients, and the machines where they run.

A regular script often follows “start → finish a job → exit.” A service process keeps listening on a port. When a request arrives, it runs the matching function and returns the result. For example, POST /verify is an HTTP request. The host and port select the service. The path selects an endpoint, and the JSON body carries the data for this call.

GYM SERVING

Turn a Python component into an HTTP service

FastAPI maps URLs to Python functions. Uvicorn listens on a port and handles network connections. An Agent Server may only run control logic. A Resources Server may spend most of its time waiting for containers and tests.

gym env start starts the configured Gym services. Successful startup does not mean a task has finished.

MODEL SERVING

Load weights onto GPUs and generate tokens

Inference backends such as vLLM and NIM load model weights, manage GPU memory and request queues, and run inference. Gym's Model Server sits in front of the backend. It adapts protocols, handles request parameters, and links calls to trajectories.

If you already have a model endpoint, Gym connects to it. Starting Gym's model proxy does not allocate GPUs, submit Slurm jobs, or load a checkpoint.

04

Async: while one task waits, another can continue

Waiting for the network, model, or container often takes much longer than the Python computation itself.

Think of the event loop as a scheduler. When a coroutine reaches an await for unfinished async I/O, it yields control. It resumes there when the result arrives. The order within that coroutine stays the same: create the sandbox before connecting to it; receive a model's tool call before running that tool.

Concurrency does not mean all computation runs in parallel

A Python event loop executes one task's Python code at a time. Waiting can overlap. Model batching and computation across multiple GPUs belong to a different layer of scheduling.

Calling synchronous network functions inside async def, or calling time.sleep(), still blocks that event loop. Using asyncio.to_thread() for a synchronous function can avoid this, but canceling the wait does not automatically stop that thread or a remote process.

Semaphore: limit concurrent work

Allowing two tasks to run at once does not mean there are two GPUs. It also does not guarantee that at most two containers exist. A concurrency limit applies only at the layer where it is placed.

In this recipe, Hermes (the agent in chapter 09) uses sem to limit activations only. Resources seed and agent seed happen before it, so this limit does not cover them. To control resource use across whole episodes, check Collector limits and the Environment’s limits on active episodes.

No. The second call starts only after the first returns. To overlap them, schedule multiple tasks first, then await their results. Use concurrency limits to protect downstream services. Async lets work yield while waiting; it does not decide which steps are safe to overlap. Here A and B are new coroutines created at each call. If you schedule them with create_task first, they can still interleave when you await their results one by one. The small experiment below compares both patterns.

"""A standard-library-only async lesson. No HTTP, Gym, GPU or subprocesses.

Run: python3 async-mini-lab.py
Predict peak_in_flight first: sequential=1, scheduled=4, bounded=2, blocking=1.
The counter includes waiting operations; it does not count CPUs or threads.
Elapsed seconds are illustrative measurements, never benchmark assertions.
"""

import asyncio
import json
import time


async def run_case(mode: str) -> dict[str, object]:
    in_flight = 0
    peak_in_flight = 0
    events: list[str] = []
    semaphore = asyncio.Semaphore(2)

    async def operation(name: str) -> None:
        nonlocal in_flight, peak_in_flight
        in_flight += 1
        peak_in_flight = max(peak_in_flight, in_flight)
        events.append(f"{name}:start")
        try:
            if mode == "blocking":
                time.sleep(0.12)  # Deliberate anti-example: occupies the loop's thread.
            else:
                await asyncio.sleep(0.12)  # Simulates waiting; no actual network I/O.
        finally:
            events.append(f"{name}:end")
            in_flight -= 1

    async def bounded(name: str) -> None:
        async with semaphore:
            await operation(name)

    started = time.perf_counter()
    if mode == "sequential":
        for name in "ABCD":
            await operation(name)
    elif mode == "scheduled":
        tasks = [asyncio.create_task(operation(name)) for name in "ABCD"]
        for task in tasks:
            await task  # Already scheduled: these await statements do not serialize starts.
    else:
        worker = bounded if mode == "bounded" else operation
        await asyncio.gather(*(worker(name) for name in "ABCD"))
    return {
        "mode": mode,
        "peak_in_flight": peak_in_flight,
        "elapsed_seconds": round(time.perf_counter() - started, 3),
        "events": events,
    }


async def main() -> None:
    entered: list[bool] = []

    async def probe() -> None:
        entered.append(True)

    coroutine = probe()  # Creates a coroutine object, without scheduling its body.
    await asyncio.sleep(0)
    print(json.dumps({"created_coroutine_has_started": bool(entered)}))
    await coroutine  # Consume it, so no unawaited-coroutine warning remains.
    for mode in ("sequential", "scheduled", "bounded", "blocking"):
        print(json.dumps(await run_case(mode)))


if __name__ == "__main__":
    asyncio.run(main())

For a small standalone service, you can create app = FastAPI(), register routes with decorators, and start it with Uvicorn. Gym adds shared configuration, clients, sessions, error handling, and observability.

When reading Gym code, start with the handler as ordinary Python, then follow the shared infrastructure. When building a Gym component, inheriting a base class saves repeated protocol and lifecycle code.

Instance fields in one process are not shared across workers. If you add workers, check where state and concurrency limits apply.

"""Prepare native Collector inputs; this tutorial helper makes no HTTP calls."""

import argparse
import json
from pathlib import Path
from uuid import uuid4

from nemo_gym.episode_types import MaterializedTask, TaskId
from nemo_gym.single_agent_turn_types import SingleAgentTurnTaskInput


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("input", type=Path)
    parser.add_argument("output_dir", type=Path, help="A new run directory; existing paths are refused")
    parser.add_argument("--limit", type=int, default=1, help="Number of tasks; 0 selects all")
    args = parser.parse_args()
    if args.limit < 0:
        parser.error("--limit must be nonnegative")
    taskset = f"swebench_pro:{uuid4().hex}"
    tasks = []
    seen = set()
    with args.input.open() as source:
        for line in source:
            row = json.loads(line)
            task = MaterializedTask[SingleAgentTurnTaskInput](
                task_id=TaskId(taskset=taskset, task_id=row["instance_id"]),
                task_input=SingleAgentTurnTaskInput(
                    responses_create_params=row["responses_create_params"],
                    task_data={
                        k: v for k, v in row.items()
                        if k not in {"responses_create_params", "agent_ref", "task_source", "skills_ref"}
                        and not k.startswith("_ng_")
                    },
                ),
            )
            if task.task_id.task_id in seen:
                raise ValueError(f"Duplicate instance_id: {task.task_id.task_id}")
            seen.add(task.task_id.task_id)
            tasks.append(task.model_dump(mode="json", exclude_unset=True))
            if args.limit and len(tasks) >= args.limit:
                break
    if not tasks:
        raise ValueError("Input contains no tasks")
    args.output_dir.mkdir(parents=True, exist_ok=False)
    with (args.output_dir / "tasks.jsonl").open("x") as output:
        for task in tasks:
            output.write(json.dumps(task) + "\n")
    # JSON is valid YAML; quoting the run-unique taskset avoids YAML key ambiguity.
    with (args.output_dir / "routing.yaml").open("x") as output:
        json.dump({
            "environment_routing_mode": "taskset",
            "environment_server_routes": {taskset: "single_agent_turn"},
        }, output, indent=2)
        output.write("\n")
    print(f"Prepared {len(tasks)} task(s) in {args.output_dir}; taskset={taskset}")


if __name__ == "__main__":
    main()

Container execution and cluster submission are separate layers

Why “sandbox provider” instead of “sandbox server”?

A provider is a replaceable implementation of capabilities. A server is a process that listens for requests. AsyncSandbox calls the provider’s create / connect / exec / stop methods. Measure a fixed policy

The training framework uses rollouts and rewards to update the policy

Gym provides environment interactions, trajectories, and rewards. Frameworks such as NeMo RL and VeRL handle optimization, gradients, and weight updates. The chosen training setup must also coordinate how updated weights reach the inference service.

Lifecycle: completion, retries, and scoring are separate

Session and cleanup code has to account for uncertain behavior in remote systems. That is why there is so much of it.

How identity works during retries

Recall chapter 02: TaskId identifies the problem, rollout_id identifies one logical sample, and attempt distinguishes executions after recovery. The corresponding capture_key looks like r42, r42-a1, and so on.

Within the same live Hermes session, retrying an activation with the same capture key and request body joins the existing state.task. A changed body gets 409. This guarantee does not cover replaying the whole Environment /run call or restarting the service process. Before creating a new attempt, inspect the original execution's state and the Collector records.

Cookies and descriptors have different jobs

The session cookie lets Resources retrieve the task's server-side state. SandboxAccess carries the provider reference, serialized connection descriptor, and workdir=/app so Agent can connect to the same sandbox.

A descriptor contains connection details. It does not copy the container or transfer lifecycle ownership. A borrower uses disconnect(); the owner uses stop().

Why close the agent before verification?

Suppose a shell tool starts a background process. The model says “I'm done,” but the process keeps writing files. Exporting a patch now would race with those writes and could affect scoring. The new path first gets Agent's close receipt and confirms runner cleanup. Resources then exports the patch, stops the task sandbox, and uses a fresh sandbox for grading. An HTTP response does not prove that the remote process tree has stopped.

There is no single timeout for everything

REQUEST / COMMAND

How long can one call wait?

The model HTTP timeout limits one model request. The terminal timeout limits one shell command. Increasing either will not fix a wrong address.

Runner / Episode

How long can the whole process run?

The runner budget limits the Hermes loop. The episode also includes seed, agent close, and verify. If the outer budget is too short, it cancels the task before the inner work finishes.

Cleanup / TTL

How long can resources remain after a stop?

Cleanup has its own time limit, separate from the episode deadline. The sandbox lease must cover its actual lifetime. A timeout response does not mean the container has disappeared.

Why not simply add more FastAPI workers?

A worker is a service process, not a coroutine. In this version, the Pro session map is an in-process dictionary, so num_workers != 1 raises an error. Hermes sessions also require one worker. A request sent to another process cannot find the session in the original process.

Environment supports multiple workers, but each has its own semaphore and queue for waiting episodes. Total capacity is roughly workers × max_concurrent_episodes. More workers do not remove the limits of stateful downstream services. First tune Collector and episode concurrency and observe downstream capacity. Then consider state sharing or routing across processes.

Code detail: can async with clean up a borrowed sandbox?

First check what the context manager does on exit. In this version, AsyncSandbox.__aexit__() always calls stop(), including on objects returned by connect(). A borrower must not destroy the task container this way. Hermes first confirms that its runner has stopped and keeps the cleanup evidence, then calls disconnect(). Resources still needs to export the patch before it stops the sandbox.

"""Prepare one typed request offline; no serving, HTTP calls, or model execution."""

import argparse
import json
from pathlib import Path
from uuid import uuid4

from nemo_gym.single_agent_turn_types import SingleAgentTurnRequest


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("input", type=Path)
    parser.add_argument("output", type=Path)
    parser.add_argument("--row", type=int, default=0, help="Zero-based JSONL line index")
    parser.add_argument("--taskset", default=None, help="Keep fixed for one run")
    parser.add_argument("--rollout-id", default=None, help="Keep fixed across attempts of one rollout")
    parser.add_argument("--attempt", type=int, default=0)
    args = parser.parse_args()
    if args.row < 0:
        parser.error("--row must be non-negative")
    with args.input.open() as stream:
        row = next((json.loads(line) for i, line in enumerate(stream) if i == args.row), None)
    if row is None:
        parser.error("--row is outside the input file")
    # Routing belongs to the caller/config. Resources receives the task fields.
    excluded = {"responses_create_params", "agent_ref", "task_source", "skills_ref"}
    request = SingleAgentTurnRequest.model_validate({
        "episode_id": {
            "rollout_id": args.rollout_id or f"tutorial-{uuid4().hex}",
            "attempt": args.attempt,
        },
        "task": {
            "task_id": {
                "taskset": args.taskset or f"swebench_pro:tutorial-{uuid4().hex}",
                "task_id": row["instance_id"],
            },
            "task_input": {
                "responses_create_params": row["responses_create_params"],
                "task_data": {
                    key: value for key, value in row.items()
                    if key not in excluded and not key.startswith("_ng_")
                },
            },
        },
    })
    # Refuse to overwrite a previously materialized identity/request.
    with args.output.open("x") as stream:
        stream.write(request.model_dump_json(indent=2) + "\n")
    print(f"Prepared {args.output}; no model call was made")


if __name__ == "__main__":
    main()

Check your understanding of the repository

① Does a ResourcesServer always need a container?

No. It manages task resources and verification. The weather example just returns a Python object. The task determines whether a sandbox is needed.

② How do an instance name, implementation directory, and upstream model name differ?

The instance name identifies a node in this configuration. The implementation directory selects the code to load. The upstream model name identifies the model sent to the inference service. For example, policy_model can be the instance name of a vllm_model proxy.

③ Why is reading only nemo_gym/ not enough to understand a benchmark?

The shared library provides reusable mechanisms. Components and recipes supply task data, tools, and scoring rules. Reading only one app.py also misses shared startup, routing, and collection behavior.

④ Does every /run use the same base-class lifecycle?

No. A native Environment wraps run with BaseEnvironmentServer's run_request. legacy_agent registers its own forwarding route to the older Agent.run. Check each setup_webserver to see which path it uses.

Check your understanding of the benchmark

① The model says “fixed,” but the patch is unchanged. Which should you trust?

Trust the actual state and verifier. SWE-Pro exports the candidate patch from the task sandbox's git diff and grades it in a clean environment. A claim in the final answer does not prove that a test passed.

② Why can raising async concurrency from 2 to 32 make a run slower?

The model queue, container capacity, connection pool, or test resources may saturate first. That increases waits and timeouts. Coroutines can wait on more requests, but they do not add downstream capacity. Measure stage latency and resource use before changing limits.

③ Why is it a bug if Agent stops a borrowed sandbox?

Resources still needs to extract the repository changes. Agent should clean up its own processes, then disconnect. Resources owns the task sandbox and stops it after exporting the patch.

④ Do the native entry example in chapter 13 and the recorded run in chapter 11 validate the same things?

No. Both use Environment → hermes_agent native sessions. The recorded run still used an outer flat-row adapter; chapter 13 accepts typed requests directly. Their source versions and budgets also differ. A real run has validated the internal lifecycle, but this new entry-point setup has not run end to end with a model.

What to check next time
Read the task contract first. Does grading consume a file or patch, or a running service? Decide whether the service belongs to the task or the agent. Identify who keeps it alive during grading and who removes it afterward. Reproduce the boundary with a small probe that spans close(), not only a check inside the agent.
Keep this distinction in mind
Stopping the agent before exporting a SWE-Pro patch makes sense. That does not mean every benchmark should kill all background services, or that skipping cleanup is a complete fix.

Case G · Capture / usage

Unknown, zero, and double-counted usage are different

The task score looks normal, but token usage is 0, null, or exactly twice the value returned by the model.

What the records showed
Historical smoke tests found per-call usage added to a final cumulative total, counting it twice. They also found missing reasoning tokens. Another run kept usage unknown for 81 successful calls instead of filling it with 0.
What to check next time
Match each actual model request to the provider’s usage record and the harness summary. Check whether each field is a per-call value or a running total. State whether the totals include the main loop, summaries or compression, delegated agents, retries, and judges. Keep missing values null and report how many calls have usage records.
Keep this distinction in mind
Matching usage totals does not prove that token IDs, logprobs, or training traces are complete. A completed task can still have missing turns in its exported training data.

Case H · Study / controlled comparison

Compare the conditions before comparing harnesses

The same model and task set yield a few more passes with harness A than B. Can we conclude that A is better?

What the records showed
Historical comparisons differed in CPU and memory limits, prompts, budgets, runtimes, and interruptions. Some resource settings were scheduling reservations; others were hard container limits. Those comparisons measured the full run recipe.
What to check next time
Pin the source, model and sampling settings, tasks and images, prompts, time limits, and actual resource limits. Report tasks graded on both sides and tasks missing from either side. Keep the original planned denominator. One repeat cannot establish that a small score gap is stable.
Keep this distinction in mind
The same model name does not control every variable. One score gap is not evidence that an architecture change caused an improvement.

Report passes with reference-answer exposure separately

What the records showed
A historical audit preserved original passing records with confirmed reference-answer exposure and marked them separately. It neither changed the rewards silently nor certified them as independent solutions.

Check task files, mount scope, material reachable over the network, and actual tool outputs. Record what the agent saw, whether it happened before or after implementation, and which traces were audited. Define access rules and reporting criteria before the benchmark.

Case J · During the run / final summary

When logs go quiet, find out what the run is waiting for

Nothing prints for a while. Or all tasks have records, but the final reporting process fails.

What the records showed
Historical long tasks included buffered output and compute loops. In another run, collection finished but finalization failed from insufficient memory. HTTP 410 or exit 143 alone does not prove an OOM or eviction.
What to check next time
Record the last successful boundary. Distinguish generation, tools, tests, resource waits, and report writing. Check timestamps, process or container state, exit reasons, and growing artifacts. Read large files line by line where possible. Preserve evidence before attempting a clearly scoped recovery.
Keep this distinction in mind
A quiet page is no reason to restart every service. An error code alone does not establish the cause. Failed reporting does not erase completed tasks, and finished log syncing does not prove that evaluation ended correctly.
